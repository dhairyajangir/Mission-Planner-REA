# Custom ground station prototype: motor test slice (simulator only)

This records what `custom-gcs/` is, what was run, what failed on the way, and what is **not** shown. It is a prototype of one function, written because the standing instruction was to "make our own version". `AGENTS.md` says the owner decides the real requirements later, so nothing here is a requirement and nothing here replaces Mission Planner. Evidence level: simulator runs on disposable SITL only; no GUI, no real aircraft, no live link.

## What exists

- `custom-gcs/customgcs/vehicle.py`: `detect(params, mav_type)` separates copter, helicopter, QuadPlane, plane, Sub, Rover, Blimp and tracker from the heartbeat vehicle type and the parameters that hold the frame (`FRAME_CLASS`/`FRAME_TYPE`, `Q_ENABLE`/`Q_FRAME_*`, `FRAME_CONFIG`).
- `custom-gcs/customgcs/motors.py`: `plan(...)` returns the `MAV_CMD_DO_MOTOR_TEST` steps for the vehicle, following the per-vehicle rules in `Copter-Frame-Types-Trace.md`, `Plane-Frame-Types-Trace.md`, `Sub-Frame-Types-Trace.md`, `Rover-Frame-Types-Trace.md` and `Vehicle-Motor-Test-Page-Trace.md`:
  - Single (class 8) and coax (class 9) copters: six sequences, the first four on the flap servos and 5 and 6 the motors, hand-transcribed from `AP_MotorsSingle.cpp`/`AP_MotorsCoax.cpp` (`_HAND` in `motors.py`).
  - Copter and QuadPlane: param1 = test sequence, order from 45 matrix layouts generated from `AP_MotorsMatrix.cpp` (`custom-gcs/tools/gen_matrix_layouts.py`, data in `customgcs/data/matrix_layouts.json`; includes types such as Y4 that Mission Planner's `APMotorLayout.json` lacks); the output a motor is on comes from the vehicle's own `SERVOn_FUNCTION`. The tricopter sequence is hand-transcribed from `AP_MotorsTri.cpp`.
  - Sub: board-order test, zero-based outputs, armed, repeated within 500 ms.
  - Rover: 1 throttle, 2 steering, 3 left, 4 right (5, main sail, is not offered because the snapshot rejects it).
  - Scripted matrix classes (15 and 17): the test order lives in a Lua script the ground station cannot see, so the plan is discovery: up to 32 sequences, stopped at the first that moves nothing; each step must move exactly one output, no output twice, and every output the vehicle lists as a motor must be covered.
  - Helicopter: no plan, `Unsupported` with the firmware's own refusal as the reason (see the probe below). Plane, Blimp, tracker and scripted matrix classes also raise `Unsupported`.
- `custom-gcs/customgcs/link.py` and `__main__.py`: pymavlink link, whole-list parameter download, plan runner that compares the servo outputs that actually moved on `SERVO_OUTPUT_RAW` with the planned ones; `python -m customgcs info|plan|motor-test`.
- Tests: 24 pytest cases (`custom-gcs/tests/`): 22 plan/detection cases whose expected orders are orders the simulator produced earlier, and 2 for the rejection-retry path using a fake link. Run in the `Ubuntu-E` venv because pymavlink is only installed there.

## Every generated layout (attempt 5)

`custom-gcs/integration/run_all_layouts.py` sets `FRAME_CLASS` and `FRAME_TYPE` on a disposable Copter simulator (physics model chosen per class: `+`, hexa, octa, octa-quad, y6, tri, dodeca-hexa, deca), restarts without wiping, and runs the prototype's plan for each of the 43 generated class/type layouts (classes 1 to 5, 7, 12 and 14; the `default` entries and the hand-transcribed single and coax classes, run in attempt 4, are not repeated). Three workers ran side by side on simulator instances 0 to 2. Evidence and per-layout files: `sitl-evidence/custom-gcs-all-layouts/` (`summary.csv`).

- **41 of 43 matched every step**, in the order the layout tables give.
- **Class 1 types 16 and 17 (NYT_PLUS and NYT_X) did not**: the Copter answers every test with COMMAND_ACK result 4 and "Motor Test: Check frame class and type" (22 retries each). `AP_MotorsMatrix.cpp` compiles those two types only under `APM_BUILD_TYPE(APM_BUILD_ArduPlane) || APM_BUILD_UNKNOWN`, so a Copter build has no motors for them and the motor library is never initialised. My generator did not read the `#if` and put them into the table, so this was a fault in the generated data, found by the run. The planner now refuses them on a Copter with that reason, and a QuadPlane run (`quadplane-layout-1-16.txt`, `quadplane-layout-1-17.txt`) matched 4 of 4 for both, so the layouts are right for the vehicle that can use them.
- Mission Planner's own `APMotorLayout.json` does list both types for class 1 (checked in the file), so its Motor Test page would draw buttons for frame types a Copter cannot run. I did not open the page for these two types; the mismatch is between that file and the Copter build and is not shown in the GUI.
- Single run per layout. The simulator model's physics need not fit every type; only which outputs the motor test drives was checked.

## Special cases (attempt 6): remapped outputs and scripted matrix frames

`custom-gcs/integration/run_special_cases.py`; results in `sitl-evidence/custom-gcs-special-cases/`.

- **Remapped outputs (quad plus, `SERVOn_FUNCTION` changed):** motors 1 and 2 swapped (motor 1 on output 2, motor 2 on output 1) matched 4 of 4; motor 1 moved to output 9 (output 1 disabled) matched 4 of 4. The plan reads the mapping from the vehicle's own parameters, so a pass shows the firmware follows `SERVOn_FUNCTION`.
- **Motor 4 on no output did not test what its name says.** Setting `SERVO4_FUNCTION` to 0 and restarting left motor 4 on output 4 in the downloaded parameter list (the plan expected output 4 and got it), so the firmware restored the motor function at start-up. The file is kept under its name but it is not evidence about an unassigned motor.
- **Scripted matrix frames (class 15, example Lua script installed, `SCR_ENABLE` 1):** hexadeca-octa and hexadeca-octa-cwx found 16 motors, each step moving one new output, 17 of 17 matched; dotriaconta-octaquad-x found 32 motors (33 of 33 matched). For all three, the observed output order equals the order predicted from the testing orders read from the script file itself (for dotriaconta, the loop's 4b+1, 4b+3, 4b+4, 4b+2 pattern applied by hand). The script file is the one the vehicle loaded, so this check is independent of the vehicle's behaviour, not of the script.
- **More scripted examples, all matched (each also compared with the Lua file's testing orders):** `MotorMatrix_setup.lua` (class 15, plus quad, order 3 1 4 2, 5 of 5), `MotorMatrix_fault_tolerant_hex.lua` (class 15, hexa, order 5 1 4 6 2 3, 7 of 7) and `Copter_Motors_6DoF.lua` (**class 16**, 6DoF scripting, quad X, order 1 4 2 3, 5 of 5). The planner now treats class 16 like 15 and 17.
- **`quadplane-ice` does not have unassigned motors in a fresh run.** `run-integration.sh` now includes it (`CG_ONLY=quadplane-ice`; result `quadplane-ice.txt` in the special-cases folder): all four motors are on outputs 5 to 8 and 4 of 4 matched. A separate probe on the same model read `SERVO1..8_FUNCTION` by single-name requests and by the full list, at 3 s and 20 s after start: identical, motors 1 to 4 on 5 to 8. `Plane-Frame-Types-Trace.md` says only motors 1 and 2 had outputs (5, 6) on that model, from the QuadPlane sweep; I could not reproduce that and have not found why (the sweep read the parameters by single-name requests right after connecting, but the probe shows those return the same values). That earlier statement stays unresolved, and the `Q_FRAME_*` unit test that borrowed its shape is now marked synthetic.
- **A motor with no output has therefore still not been tested in a simulator.** Parameters cannot unassign it on a Copter (the firmware puts the function back), and the one model that seemed to have it does not in a fresh run.
- **Faults found on the way, attempts kept:** (1) first dotriaconta run, `...-run1-exception-outputs-above-16-not-read.txt`: the Lua comparison raised an exception because only outputs 1 to 16 have `SERVOn_FUNCTION` parameters, so the plan (built from assigned motors) had 16 steps for a 32-motor frame (`...-run2-plan-limited-to-16-assigned-outputs.txt`, which also shows the 16-motor limit). The planner now discovers the count instead of reading it. (2) `SERVO_OUTPUT_RAW` carries 16 outputs per message and a `port` field; outputs 17 to 32 arrive as port 1. My reader treated every message as outputs 1 to 16, which would have mixed the two ports on a 32-output frame; it now keeps all 32 by port. (3) `...-run3-discovery-ok-lua-comparison-keyerror-above-16.txt`: the discovery found 32 motors but my comparison indexed a mapping that does not exist above output 16; the comparison now assumes motor n is on output n there, as the earlier sweep did.
- **Regression after the reader change:** the 13-simulator run was repeated (`sitl-evidence/custom-gcs-integration-rerun-after-32-output-reader/`): the same 12 matches, helicopter still exits 2.

## Functions slice: parameters, arm and modes, missions (attempt 7)

Added after the owner answered "all of these" to which Copter functions to build next. Modules `custom-gcs/customgcs/params.py`, `flight.py`, `mission.py`, command line in `__main__.py`; mode table generated from `ArduCopter/mode.h` by `tools/gen_copter_modes.py` (25 requestable modes; AUTO_RTL is not a true mode). 61 unit tests pass in total (59 without pymavlink) (`tests/test_functions.py` is the new file). Evidence: `sitl-evidence/custom-gcs-functions/` (library-level run, `integration/run_functions.py`) and `sitl-evidence/custom-gcs-cli-smoke/` (the command line itself, `integration/cli-smoke.sh`), both against one disposable Copter simulator.

**What each part does**
- Parameters: save and load a `NAME,VALUE` file, diff it against the vehicle, restore the differences with a read-back and a final re-download. It writes only differing parameters, refuses an armed vehicle, supports a dry run, and does not touch protected names: serial settings, `SYSID_THISMAV`, counters, and values the vehicle maintains itself (`COMPASS_DEC`, `MIS_TOTAL`, `BARO*_GND_PRESS/TEMP`). The whole list is downloaded each time because single-name reads were unreliable earlier.
- Arm, disarm, mode: each command returns the acknowledgement and the vehicle's own STATUSTEXT reasons; arm retries a refusal for up to 60 s because start-up checks pass later; force-arm needs an explicit flag.
- Missions: items are checked before anything is sent (NaN, infinity, latitude and longitude range, sequence order) and uploaded only as `MISSION_ITEM_INT`, because `Mission-File-Trace.md` recorded a simulator abort on a NaN floating-point item. The WPL reader rejects rows that do not have 12 fields instead of skipping them as the original reader does. Verify compares from item 1; item 0 is the vehicle's home.
- Command-line guard: every command that changes the vehicle refuses a host other than the local machine unless `--allow-remote` is given.

**Library run (one simulator, 5 minutes): all 23 checks passed** after the first attempt's faults were fixed (below). Observed behaviour worth keeping:
- Parameters: three changed parameters (`PILOT_SPD_UP`, `RTL_ALT_M`, `LAND_SPD_MS`) were echoed by the vehicle, the diff listed exactly those, a dry run wrote nothing, a restore put them back with the protected `SERIAL0_BAUD` skipped, and the vehicle then matched the saved file. A parameter the vehicle does not have gets no echo and is reported.
- Modes, requested one at a time on the ground. **Disarmed:** 18 accepted; refused with `init failed`: FLIP, AUTOTUNE, FLOWHOLD, FOLLOW (text "Set FOLL_ENABLE = 1"), SYSTEMID ("No axis selected, SID_AXIS = 0"), TURTLE; AUTOROTATE "No such mode 26" (this is the plain Copter build, not the helicopter one). **Armed (on the ground, in the simulator):** the same refusals plus AUTO ("init failed"; AUTO was accepted disarmed). I did not establish why AUTO differs; the vehicle's text gives no reason, and the mission was empty. Acceptance only: nothing was flown and no behaviour inside a mode was checked.
- Arm: about 15 s after start the first arm was refused ("Arm: Accels inconsistent") and a retry within 6 s was accepted; later, after position estimate came, arm was accepted (the command-line run shows "Arm: Need Position Estimate" refusals before acceptance).
- Missions: five items uploaded (ack 0) and downloaded back equal from item 1; a NaN latitude was refused before sending and the vehicle's stored mission was unchanged; an item with unknown command 9999 was answered with ack type 3; clear gave ack 0 and a later download returned 0 items (no home item).
- The vehicle rewrites the frame of a location-less item: an RTL item sent with frame 3 came back with frame 0. Verify therefore skips the frame of items without a location.

**Command-line smoke (19 commands, exit codes as designed):** `info`, `modes`, `params-save`, `params-diff` (0 differences, then 1 after editing the file: exit 1), dry-run and real `params-restore`, `mode LOITER` (accepted), `mode FLIP` (refused with the vehicle's reason, exit 1), `arm`, `params-restore` while armed (refused, exit 4), `disarm`, `mission-upload`, `mission-verify`, `mission-download`, `mission-clear`, a mission file with NaN (refused before sending, exit 4), `arm --host 10.1.2.3` (refused, exit 3).

**Faults found by the runs, attempts kept**
1. `functions-run1-*`: I used parameter names from an older ArduPilot (`WPNAV_SPEED`, `ANGLE_MAX`, `RTL_ALT`); this snapshot has `PILOT_SPD_UP`, `RTL_ALT_M`, `LAND_SPD_MS`, so the parameter section raised a `KeyError`. The first arm at 15 s succeeded and left the vehicle armed for the "disarmed" mode sweep, so that sweep was not what it said; the driver now disarms and checks. Verify compared the frame of the RTL item and failed on the vehicle's frame rewrite. Fixed: names, disarm and check, location-less frame rule.
2. `cli-smoke-run1-*`: after `params-save`, `params-diff` immediately listed `COMPASS_DEC`, and a restore tried to write `BARO1_GND_PRESS`, `BARO2_GND_PRESS` and `MIS_TOTAL` back and the vehicle refused (kept its own values). These are values the vehicle updates itself. They are now treated as vehicle-maintained: shown but flagged in a diff, never written by a restore, and a difference only in them is not a failure.
3. A restore while armed raised a traceback in the command line; errors from refusals and bad files are now printed as `error: ...` with exit 4.

**Not shown:** anything on real hardware; behaviour of any mode after it is entered; flying a mission (AUTO with a mission, takeoff, waypoints); geofence, rally points and other mission types; parameters on any vehicle but the Copter simulator (the code is vehicle-agnostic for parameters and missions, but only this one was run); writing parameters that need a reboot to take effect; one run per attempt. The mode sweep depends on this snapshot's `mode.h` (a firmware with other modes needs the table regenerated).

## Flying an uploaded mission in the simulator (attempt 8)

`custom-gcs/integration/run_flight.py` uploads a five-item mission (home, TAKEOFF to 15 m, a waypoint 78 m north of home, a waypoint 82 m east of that, RETURN_TO_LAUNCH), arms in STABILIZE, switches to AUTO, sends `MAV_CMD_MISSION_START` (new `flight.start_mission`, command `mission-start`), and follows `MISSION_ITEM_REACHED`, `GLOBAL_POSITION_INT` and the heartbeat on a disposable Copter simulator at real-time speed. Evidence: `sitl-evidence/custom-gcs-flight/` (`flight-run.txt`, `flight-track.csv`) and one repeat, `custom-gcs-flight-repeat/`.

**Result, both runs: all checks passed.** Items 1 to 4 were reached in order; the two waypoints were reached 1.3 m and 0.7 m from their uploaded coordinates (the vehicle's acceptance radius is `WP_RADIUS_M`, 2 m), at 15.0 m relative altitude; item 1 (takeoff) completed 5 s after the mission start, item 2 at 18.5 s, item 3 at 31.5 s, the RTL descent ended with the vehicle's own "SIM Hit ground at 0.5 m/s" and an automatic disarm 83 s after the start, at the home position. The two runs agree to a few decimetres and a fraction of a second, which fits a deterministic simulator; this is not independent evidence of repeatability on a vehicle.

**Four earlier attempts, all kept, each a fault of mine:**
1. `run1`: I asked the vehicle to stream `MISSION_ITEM_REACHED`; it then repeated sequence 65535 (which is not an item) and my loop counted those, and at speedup 3 the vehicle's 10 s auto-disarm (`DISARM_DELAY`) ran out within about 3 s of wall-clock time.
2. `run2`: AUTO was refused (ack 4) because I armed before the vehicle had a position estimate; the driver now waits and retries AUTO for up to 90 s.
3. `run3` and `run4`: AUTO was accepted and the mission announced "Mission: 1 Takeoff", but the vehicle never lifted and disarmed itself after about 9 s. Cause (established by the next run, not by reading the source): a Copter armed in AUTO on the ground does not take off until the mission is started or the pilot raises the throttle. Run 3 also waited 900 s for nothing because the end-of-flight test could not trigger; the loop now stops when the vehicle is disarmed and nothing was reached after 30 s.

**Not shown:** anything on a real vehicle; wind, GPS or battery failure; other mission commands (loiter, jump, speed changes, conditional or DO commands); a mission longer than three legs; flying with the vehicle's failsafes triggered; the same mission at other speedups (speedup 1 only after the attempts above). The pass criteria are the ones in `run_flight.py` and were written before the passing run but after four failed ones.

## Geofence and rally points, and a flight into a fence breach (attempt 9)

`mission.py` now takes a mission type (0 mission, 1 geofence, 2 rally points) in upload, download and clear, filters replies of the other types, and has `fence_polygon` and `rally_points` helpers; `verify(..., skip_home=False)` compares item 0 for lists without a home. Command line: `--list mission|fence|rally` on the `mission-*` commands. `integration/run_fence_rally.py`; evidence `sitl-evidence/custom-gcs-fence-rally/` (`fence-rally-run.txt`, `fence-flight-track.csv`). 55 unit tests pass in WSL (3 new, with a fake link that also answers a request for the wrong list first).

**Result: all checks passed.**
- Lists: a four-vertex polygon fence (a square of 60 m each way around home) and two rally points uploaded (ack 0) and downloaded back equal; the vehicle then reported `RALLY_TOTAL` 2 and `FENCE_TOTAL` 6; clearing the rally list gave ack 0 and an empty list; the ordinary mission list was untouched by the other two lists.
- Flight: with the fence enabled (`FENCE_ENABLE` 1, `FENCE_ACTION` 1) and a mission whose first waypoint is 78 m north of home (outside the polygon), the vehicle took off, reached item 1, and 10 s later reported "Polygon fence breached"; the heartbeat mode went from AUTO to RTL in the same second ("Manual recovery started"), the breach cleared 10 s later, and the vehicle descended to the ground and disarmed. Waypoint 2 was never reported reached. It ended 0.0 m from rally point 1, 52 m from home, inside the fence: the return went to the nearer rally point, not to home.

**Not shown:** the fence action values other than 1 (report only, always land, SmartRTL or RTL or land, brake or land); circle and exclusion fences, altitude fences; several polygons; fence breaches in modes other than AUTO; the rally point choice when home is nearer; anything on a real vehicle; one run (the run and its first attempt differ only in the check).

## Fixed-wing plane: modes, arming, parameters, a flown mission and failsafes (attempt 12)

Added after the owner said planes matter alongside copters and confirmed "Yes, planes". The mode table for ArduPlane is generated from `ArduPlane/mode.h` (`tools/gen_copter_modes.py ArduPlane`, `data/plane_modes.json`: 26 entries; the QuadPlane modes are flagged conditional on `HAL_QUADPLANE_ENABLED`); the library's mode functions now take a vehicle table (`copter`, `rover`, `plane`), so the same number means different modes per vehicle (4 is GUIDED on a Copter, HOLD on a Rover, ACRO on a Plane). Command line: `modes --vehicle plane`, and `mode --name` picks the table from the detected vehicle kind (a QuadPlane uses the plane table). `mission.verify` gained an `ignore` list of (command, field) pairs a vehicle is known to rewrite. 61 unit tests pass in WSL (59 without pymavlink). Harness: `custom-gcs/integration/run_plane.py`; evidence `sitl-evidence/custom-gcs-plane/` (one text per part, a track CSV per flight).

**Basics (disarmed sweep, arming, parameters): passed.** Of the 25 requestable modes, 15 were accepted disarmed; refused: QSTABILIZE, QHOVER, QLOITER, QLAND, QRTL, QAUTOTUNE, QACRO and AUTOLAND with "Q_ENABLE 0" (this is not a QuadPlane), THERMAL with "Flight mode change failed", and AUTO, which answered ack 0 but the vehicle stayed in RTL (no mission was loaded). ## A local screen for the prototype (attempt 17)

`python -m customgcs ui [--connect --port 5760]` serves a page on `127.0.0.1:8765` (`customgcs/webui.py`, `customgcs/data/ui.html`; tests `tests/test_webui.py`). It drives the same library functions as the command line, so it works for the vehicles that have a mode table (Copter, helicopter build, Plane, QuadPlane, Rover). It shows connection, vehicle, mode, armed state, position, height and speed, attitude, GPS, battery, mission item and the vehicle's own messages; a position trail with the mission waypoints and home (north up, metres from home, no map tiles); a mode selector filled from the detected vehicle, arm, disarm, mission start, and a "Fly the mission" button (leave AUTO if needed, arm, AUTO, start, in one go, because a vehicle left armed on the ground disarms itself after about 10 s); mission, fence and rally upload, download and clear as QGC WPL text, with an example mission; parameters (load, filter, save a `.param` file, change one value with the same protections as the library, refused while armed). There is no force-arm button.

**Safety design:** one worker thread owns the MAVLink connection; the server binds to `127.0.0.1` only, accepts only a Host header naming this machine, and requires a random token (placed in the page when it is served) on every POST, so another web page open in the same browser cannot drive the vehicle through it. The vehicle connection is always to `127.0.0.1`. 13 unit tests cover the state parsing, the message wrapper (which updates the display from every message the library reads), the token and host checks and the loopback-only binding.

**Run on a Copter simulator** (`sitl-evidence/custom-gcs-screen/`): connected from the page (vehicle detected as a Copter, 25 modes listed), the example mission uploaded, and the one-button flight armed, entered AUTO and started the mission; the page showed the vehicle at 15 m and 7.2 m/s on mission item 3 and the screenshot `copter-mission-flight-in-progress.jpg` shows the trail north then east, the return leg, the waypoints and the vehicle's messages ("Reached command #2", "#3", "Mission: 4 RTL"). One run, one vehicle, one browser; I checked the page by reading its state and one screenshot, not with a full visual or accessibility review, and not at phone width.

**Faults found while running it, kept honestly:**
1. The mode list was empty when the page loaded after the server had already connected (it was filled only by the Connect button's reply); the list now comes with the state.
2. A position at latitude 0, longitude 0 before the GPS fix was plotted as a line from the far side of the world; such positions are now ignored.
3. A rejected POST (wrong token or host) was answered before its body was read, which on Windows could reset the client's connection and made one test fail intermittently (it passed on rerun, then failed again once); the body is now read first and the test passed three times in a row.
4. Arm then AUTO by two clicks took longer than the vehicle's 10 s auto-disarm ("Arming motors", "Disarming motors"): the first flight attempt from the page did not fly (`copter-connected-uploaded-mission-before-flight-attempt-that-auto-disarmed.jpg`). That is the vehicle's behaviour, not a page error, and it is why the one-button flight exists.
5. The one-button flight first failed with "Arm: Auto mode not armable" because the vehicle was still in AUTO from the previous try; it now leaves AUTO first (STABILIZE for a Copter, MANUAL for a Plane). The page showed the vehicle's own refusal reason, which is how this was found.
6. A simulator I started as the foreground of a hidden process exited by itself; starting it as a background job of a script that waits (the pattern the test scripts use) kept it alive. This is about my launching of the simulator, not the screen.

**Not shown:** the screen against a Plane or any other vehicle; use on any host other than this machine's simulator (it refuses by construction); several users or browsers at once; anything on real hardware; a polished design review (it follows a plain, theme-aware layout with labelled controls and keyboard focus styles, not tested with a screen reader); parameter writing from the page was not exercised in the browser (the library path was run earlier).

## What this does and does not show

- Shown: for those twelve simulated frames (and the helicopter's refusal), the plan the prototype derives from the vehicle's own parameters moves exactly the predicted outputs, in the predicted order, with the prototype's own ACK handling.
- Not shown: any other frame (the earlier sweeps cover more), any flight, any real autopilot or motor, any GUI, calibration, parameter editing, mission or map function. Plane, Blimp, tracker and scripted matrices are explicitly unsupported and the helicopter has no motor test to plan. Every generated copter layout and the three scripted example frames were run once; two remapped-output cases were run once. Not shown: a motor with no output at all, scripted frames other than the six examples, and anything on real hardware. The unit-test orders and the integration orders come from the same earlier sweeps, so a shared misreading would not be caught by either.
- The check `moved` uses a 20 microsecond change threshold on `SERVO_OUTPUT_RAW` and ignores outputs that are not motor, throttle, tilt or steering functions; a failure to move something outside that set is not detected.
- The motor test spins motors. It was run against simulators only and must not be run with propellers fitted or against a real aircraft.


## QuadPlane failsafes during VTOL, transition and landing (attempt 18)

`run_quadplane_failsafes.py`: six scenarios on a disposable QuadPlane simulator (the known VTOL-takeoff/transition/waypoints/VTOL-land mission), one fault each at a named flight phase. My pass/fail checks guessed the expected resulting mode before running them; four of the six guesses were wrong, and the real, observed behaviour (kept in full in the result texts and tracks, `sitl-evidence/quadplane-failsafes/`) is the finding:

| Scenario | Fault, phase | What actually happened |
|---|---|---|
| GCS link loss, during the transition | FS_GCS_ENABL 1, heartbeats stopped 16 s after AUTO (mid-transition) | 4.6 s later "GCS Failsafe On: switched to RTL" (my guess was right, this one passed): the failsafe is not disrupted by being mid-transition. |
| Battery low, VTOL hover phase | BATT_FS_LOW_ACT 1 (RTL), BATT_LOW_VOLT 11, voltage set to 10.5 at 6 s (still hovering) | no "Battery" failsafe text at any point; the mission continued through the transition, both waypoints and a normal VTOL landing. I expected QLAND, which was simply the wrong guess, but no failsafe of any kind fired, which the earlier Plane-only test (2.0 s reaction) did not show. |
| Battery low, cruise phase | same, fault injected at 31 s (after the transition, in level flight) | the same: no battery failsafe text, mission and landing completed normally. Two runs, same result; the parameter writes were both confirmed applied (no rejection). |
| GPS loss, VTOL hover phase | FS_EKF_ACTION 1, GPS disabled 6 s in | the parameter write was refused: ArduCopter has an "FS_EKF_ACTION" parameter (ArduCopter/Parameters.cpp, GSCALAR fs_ekf_action) that ArduPlane does not; ArduPlane only has FS_EKF_THRESH, no configurable action. So this scenario ran with no failsafe action configured at all. The EKF showed internal reactions ("AHRS: DCM active", "EKF3 IMU0/IMU1 stopped aiding", a lane switch) but no mode change; the mission continued to a VTOL landing that ended with the simulator reporting ground contact at 2.7 m/s, higher than the roughly 0.5 m/s of a normal landing in every other run here. One run; not enough to say the harder touchdown was caused by the GPS loss. |
| GPS loss, cruise phase | same (also refused for the same reason), fault at 31 s | the same EKF reactions, no mode change, mission completed and landed normally (about 0.5 m/s, unlike the VTOL-phase case above). |
| RC loss, during the VTOL landing approach | SIM_RC_FAIL 1, injected right as "VTOL approach" began | "RC Short Failsafe On" at 1.2 s, then "RC Long Failsafe On: switched to Auto" at 5.3 s: the vehicle stayed in (or returned to) AUTO and continued the landing already in progress, rather than diverting to RTL as the plain-Plane RC-loss test (during cruise, not a landing) does. My guess was RTL, which was wrong for this phase; the real finding is that RC long failsafe does not abandon an AUTO landing sequence already under way. |

**Resolved:** the battery-low failsafe did not fire because `default_params/quadplane.parm` never sets `BATT_MONITOR` (the compiled default is `Type::NONE`, `AP_BattMonitor_Params.cpp`; `models/plane.parm`, used by the plain-Plane test, sets it to 4), so no battery was monitored at all and `SIM_BATT_VOLTAGE` was never read by anything. `research-tools/sitl-quadplane-battery-monitor-confirm.py` confirms this: setting `BATT_MONITOR` live with no reboot could not arm (`BATT_MONITOR` is an enable-flag parameter, needs a reboot, the same pattern as `SERVO_DSHOT_ESC`/`SOAR_ENABLE`/`AROT_ENABLE`/`Q_TAILSIT_ENABLE` elsewhere in this project; that attempt is kept, `sitl-evidence/quadplane-battery-monitor-confirm-run1-no-reboot/`); with a proper two-stage boot (set, restart, then arm), the same scenario fired the failsafe in 1.2 s ("Battery 1 is low 9.94V used 165 mAh", mode to RTL), during the transition. So this was a configuration gap in the stock `quadplane.parm`, not a QuadPlane-specific firmware suppression. **Not shown:** why `quadplane.parm` omits `BATT_MONITOR` (not investigated); ArduPlane's own EKF/GPS failsafe mechanism (there is no FS_EKF_ACTION to configure; FS_EKF_THRESH alone was not tested here); whether the harder VTOL-phase GPS-loss touchdown (2.7 m/s) was caused by the fault (one run); any fault during the VTOL landing itself other than RC loss; two faults together; anything on a real aircraft. One run per scenario.
