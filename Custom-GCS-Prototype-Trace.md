# Custom ground station prototype: motor test slice (simulator only)

This records what `custom-gcs/` is, what was run, what failed on the way, and what is **not** shown. It is a prototype of one function, written because the standing instruction was to "make our own version". `AGENTS.md` says the owner decides the real requirements later, so nothing here is a requirement and nothing here replaces Mission Planner. Evidence level: simulator runs on disposable SITL only; no GUI, no real aircraft, no live link.

## What exists

- `custom-gcs/customgcs/vehicle.py`: `detect(params, mav_type)` separates copter, helicopter, QuadPlane, plane, Sub, Rover, Blimp and tracker from the heartbeat vehicle type and the parameters that hold the frame (`FRAME_CLASS`/`FRAME_TYPE`, `Q_ENABLE`/`Q_FRAME_*`, `FRAME_CONFIG`).
- `custom-gcs/customgcs/motors.py`: `plan(...)` returns the `MAV_CMD_DO_MOTOR_TEST` steps for the vehicle, following the per-vehicle rules in `Copter-Frame-Types-Trace.md`, `Plane-Frame-Types-Trace.md`, `Sub-Frame-Types-Trace.md`, `Rover-Frame-Types-Trace.md` and `Vehicle-Motor-Test-Page-Trace.md`:
  - Single (class 8) and coax (class 9) copters: six sequences, the first four on the flap servos and 5 and 6 the motors, hand-transcribed from `AP_MotorsSingle.cpp`/`AP_MotorsCoax.cpp` (`_HAND` in `motors.py`).
  - Copter and QuadPlane: param1 = test sequence, order from 45 matrix layouts generated from `AP_MotorsMatrix.cpp` (`custom-gcs/tools/gen_matrix_layouts.py`, data in `customgcs/data/matrix_layouts.json`; includes types such as Y4 that Mission Planner's `APMotorLayout.json` lacks); the output a motor is on comes from the vehicle's own `SERVOn_FUNCTION`. The tricopter sequence is hand-transcribed from `AP_MotorsTri.cpp`.
  - Sub: board-order test, zero-based outputs, armed, repeated within 500 ms.
  - Rover: 1 throttle, 2 steering, 3 left, 4 right (5, main sail, is not offered because the snapshot rejects it).
  - Scripted matrix classes (15 and 17): the test order lives in a Lua script the ground station cannot see, so the plan is discovery: up to 32 sequences, stopped at the first that moves nothing; each step must move exactly one output, no output twice, and every output the vehicle lists as a motor must be covered.
  - Helicopter: no plan, `Unsupported` with the firmware's own refusal as the reason (see the probe below). Plane, Blimp, tracker and scripted matrix classes also raise `Unsupported`.
- `custom-gcs/customgcs/link.py` and `__main__.py`: pymavlink link, whole-list parameter download, plan runner that compares the servo outputs that actually moved on `SERVO_OUTPUT_RAW` with the planned ones; `python -m customgcs info|plan|motor-test`.
- Tests: 24 pytest cases (`custom-gcs/tests/`): 22 plan/detection cases whose expected orders are orders the simulator produced earlier, and 2 for the rejection-retry path using a fake link. Run in the `Ubuntu-E` venv because pymavlink is only installed there.

## Integration runs (ten disposable simulators, one run each per attempt)

`custom-gcs/integration/run-integration.sh` starts each simulator, runs `motor-test`, stops it. Frames in attempts 1 to 3: Copter quad-plus, hexa-x, octa, y6, tri; QuadPlane quadplane, quadplane-tri; Sub vectored; Rover rover-skid, sailboat. Attempt 4 adds Copter singlecopter, coaxcopter and the helicopter (`arducopter-heli`).

## Every generated layout (attempt 5)

`custom-gcs/integration/run_all_layouts.py` sets `FRAME_CLASS` and `FRAME_TYPE` on a disposable Copter simulator (physics model chosen per class: `+`, hexa, octa, octa-quad, y6, tri, dodeca-hexa, deca), restarts without wiping, and runs the prototype's plan for each of the 43 generated class/type layouts (classes 1 to 5, 7, 12 and 14; the `default` entries and the hand-transcribed single and coax classes, run in attempt 4, are not repeated). Three workers ran side by side on simulator instances 0 to 2. Evidence and per-layout files: `sitl-evidence/custom-gcs-all-layouts/` (`summary.csv`).

- **41 of 43 matched every step**, in the order the layout tables give.
- **Class 1 types 16 and 17 (NYT_PLUS and NYT_X) did not**: the Copter answers every test with COMMAND_ACK result 4 and "Motor Test: Check frame class and type" (22 retries each). `AP_MotorsMatrix.cpp` compiles those two types only under `APM_BUILD_TYPE(APM_BUILD_ArduPlane) || APM_BUILD_UNKNOWN`, so a Copter build has no motors for them and the motor library is never initialised. My generator did not read the `#if` and put them into the table, so this was a fault in the generated data, found by the run. The planner now refuses them on a Copter with that reason, and a QuadPlane run (`quadplane-layout-1-16.txt`, `quadplane-layout-1-17.txt`) matched 4 of 4 for both, so the layouts are right for the vehicle that can use them.
- Mission Planner's own `APMotorLayout.json` does list both types for class 1 (checked in the file), so its Motor Test page would draw buttons for frame types a Copter cannot run. I did not open the page for these two types; the mismatch is between that file and the Copter build and is not shown in the GUI.
- Single run per layout. The simulator model's physics need not fit every type; only which outputs the motor test drives was checked.

## Special cases (attempt 6): remapped outputs and scripted matrix frames

`custom-gcs/integration/run_special_cases.py`; results in `sitl-evidence/custom-gcs-special-cases/`.

- **Remapped outputs (quad plus, `SERVOn_FUNCTION` changed):** motors 1 and 2 swapped (motor 1 on output 2, motor 2 on output 1) matched 4 of 4; motor 1 moved to output 9 (output 1 disabled) matched 4 of 4. The plan reads the mapping from the vehicle's own parameters, so a pass shows the firmware follows `SERVOn_FUNCTION`.
- **Motor 4 on no output did not test what its name says.** Setting `SERVO4_FUNCTION` to 0 and restarting left motor 4 on output 4 in the downloaded parameter list (the plan expected output 4 and got it), so the firmware restored the motor function at start-up. The file is kept under its name but it is not evidence about an unassigned motor.
- **Scripted matrix frames (class 15, example Lua script installed, `SCR_ENABLE` 1):** hexadeca-octa and hexadeca-octa-cwx found 16 motors, each step moving one new output, 17 of 17 matched; dotriaconta-octaquad-x found 32 motors (33 of 33 matched). For all three, the observed output order equals the order predicted from the testing orders read from the script file itself (for dotriaconta, the loop's 4b+1, 4b+3, 4b+4, 4b+2 pattern applied by hand). The script file is the one the vehicle loaded, so this check is independent of the vehicle's behaviour, not of the script.
- **More scripted examples, all matched (each also compared with the Lua file's testing orders):** `MotorMatrix_setup.lua` (class 15, plus quad, order 3 1 4 2, 5 of 5), `MotorMatrix_fault_tolerant_hex.lua` (class 15, hexa, order 5 1 4 6 2 3, 7 of 7) and `Copter_Motors_6DoF.lua` (**class 16**, 6DoF scripting, quad X, order 1 4 2 3, 5 of 5). The planner now treats class 16 like 15 and 17.
- **`quadplane-ice` does not have unassigned motors in a fresh run.** `run-integration.sh` now includes it (`CG_ONLY=quadplane-ice`; result `quadplane-ice.txt` in the special-cases folder): all four motors are on outputs 5 to 8 and 4 of 4 matched. A separate probe on the same model read `SERVO1..8_FUNCTION` by single-name requests and by the full list, at 3 s and 20 s after start: identical, motors 1 to 4 on 5 to 8. `Plane-Frame-Types-Trace.md` says only motors 1 and 2 had outputs (5, 6) on that model, from the QuadPlane sweep; I could not reproduce that and have not found why (the sweep read the parameters by single-name requests right after connecting, but the probe shows those return the same values). That earlier statement stays unresolved, and the `Q_FRAME_*` unit test that borrowed its shape is now marked synthetic.
- **A motor with no output has therefore still not been tested in a simulator.** Parameters cannot unassign it on a Copter (the firmware puts the function back), and the one model that seemed to have it does not in a fresh run.
- **Faults found on the way, attempts kept:** (1) first dotriaconta run, `...-run1-exception-outputs-above-16-not-read.txt`: the Lua comparison raised an exception because only outputs 1 to 16 have `SERVOn_FUNCTION` parameters, so the plan (built from assigned motors) had 16 steps for a 32-motor frame (`...-run2-plan-limited-to-16-assigned-outputs.txt`, which also shows the 16-motor limit). The planner now discovers the count instead of reading it. (2) `SERVO_OUTPUT_RAW` carries 16 outputs per message and a `port` field; outputs 17 to 32 arrive as port 1. My reader treated every message as outputs 1 to 16, which would have mixed the two ports on a 32-output frame; it now keeps all 32 by port. (3) `...-run3-discovery-ok-lua-comparison-keyerror-above-16.txt`: the discovery found 32 motors but my comparison indexed a mapping that does not exist above output 16; the comparison now assumes motor n is on output n there, as the earlier sweep did.
- **Regression after the reader change:** the 13-simulator run was repeated (`sitl-evidence/custom-gcs-integration-rerun-after-32-output-reader/`): the same 12 matches, helicopter still exits 2.

## Functions slice: parameters, arm and modes, missions (attempt 7)

Added after the owner answered "all of these" to which Copter functions to build next. Modules `custom-gcs/customgcs/params.py`, `flight.py`, `mission.py`, command line in `__main__.py`; mode table generated from `ArduCopter/mode.h` by `tools/gen_copter_modes.py` (25 requestable modes; AUTO_RTL is not a true mode). 51 unit tests pass in total (49 without pymavlink) (`tests/test_functions.py` is the new file). Evidence: `sitl-evidence/custom-gcs-functions/` (library-level run, `integration/run_functions.py`) and `sitl-evidence/custom-gcs-cli-smoke/` (the command line itself, `integration/cli-smoke.sh`), both against one disposable Copter simulator.

**What each part does**
- Parameters: save and load a `NAME,VALUE` file, diff it against the vehicle, restore the differences with a read-back and a final re-download. It writes only differing parameters, refuses an armed vehicle, supports a dry run, and does not touch protected names: serial settings, `SYSID_THISMAV`, counters, and values the vehicle maintains itself (`COMPASS_DEC`, `MIS_TOTAL`, `BARO*_GND_PRESS/TEMP`). The whole list is downloaded each time because single-name reads were unreliable earlier.
- Arm, disarm, mode: each command returns the acknowledgement and the vehicle's own STATUSTEXT reasons; arm retries a refusal for up to 60 s because start-up checks pass later; force-arm needs an explicit flag.
- Missions: items are checked before anything is sent (NaN, infinity, latitude and longitude range, sequence order) and uploaded only as `MISSION_ITEM_INT`, because `Mission-File-Trace.md` recorded a simulator abort on a NaN floating-point item. The WPL reader rejects rows that do not have 12 fields instead of skipping them as the original reader does. Verify compares from item 1; item 0 is the vehicle's home.
- Command-line guard: every command that changes the vehicle refuses a host other than the local machine unless `--allow-remote` is given.

**Library run (one simulator, 5 minutes): all 23 checks passed** after the first attempt's faults were fixed (below). Observed behaviour worth keeping:
- Parameters: three changed parameters (`PILOT_SPD_UP`, `RTL_ALT_M`, `LAND_SPD_MS`) were echoed by the vehicle, the diff listed exactly those, a dry run wrote nothing, a restore put them back with the protected `SERIAL0_BAUD` skipped, and the vehicle then matched the saved file. A parameter the vehicle does not have gets no echo and is reported.
- Modes, requested one at a time on the ground. **Disarmed:** 18 accepted; refused with `init failed`: FLIP, AUTOTUNE, FLOWHOLD, FOLLOW (text "Set FOLL_ENABLE = 1"), SYSTEMID ("No axis selected, SID_AXIS = 0"), TURTLE; AUTOROTATE "No such mode 26" (this is the plain Copter build, not the helicopter one). **Armed (on the ground, in the simulator):** the same refusals plus AUTO ("init failed"; AUTO was accepted disarmed). I did not establish why AUTO differs; the vehicle's text gives no reason, and the mission was empty. Acceptance only: nothing was flown and no behaviour inside a mode was checked.
- Arm: about 15 s after start the first arm was refused ("Arm: Accels inconsistent") and a retry within 6 s was accepted; later, after position estimate came, arm was accepted (the command-line run shows "Arm: Need Position Estimate" refusals before acceptance).
- Missions: five items uploaded (ack 0) and downloaded back equal from item 1; a NaN latitude was refused before sending and the vehicle's stored mission was unchanged; an item with unknown command 9999 was answered with ack type 3; clear gave ack 0 and a later download returned 0 items (no home item).
- The vehicle rewrites the frame of a location-less item: an RTL item sent with frame 3 came back with frame 0. Verify therefore skips the frame of items without a location.

**Command-line smoke (19 commands, exit codes as designed):** `info`, `modes`, `params-save`, `params-diff` (0 differences, then 1 after editing the file: exit 1), dry-run and real `params-restore`, `mode LOITER` (accepted), `mode FLIP` (refused with the vehicle's reason, exit 1), `arm`, `params-restore` while armed (refused, exit 4), `disarm`, `mission-upload`, `mission-verify`, `mission-download`, `mission-clear`, a mission file with NaN (refused before sending, exit 4), `arm --host 10.1.2.3` (refused, exit 3).

**Faults found by the runs, attempts kept**
1. `functions-run1-*`: I used parameter names from an older ArduPilot (`WPNAV_SPEED`, `ANGLE_MAX`, `RTL_ALT`); this snapshot has `PILOT_SPD_UP`, `RTL_ALT_M`, `LAND_SPD_MS`, so the parameter section raised a `KeyError`. The first arm at 15 s succeeded and left the vehicle armed for the "disarmed" mode sweep, so that sweep was not what it said; the driver now disarms and checks. Verify compared the frame of the RTL item and failed on the vehicle's frame rewrite. Fixed: names, disarm and check, location-less frame rule.
2. `cli-smoke-run1-*`: after `params-save`, `params-diff` immediately listed `COMPASS_DEC`, and a restore tried to write `BARO1_GND_PRESS`, `BARO2_GND_PRESS` and `MIS_TOTAL` back and the vehicle refused (kept its own values). These are values the vehicle updates itself. They are now treated as vehicle-maintained: shown but flagged in a diff, never written by a restore, and a difference only in them is not a failure.
3. A restore while armed raised a traceback in the command line; errors from refusals and bad files are now printed as `error: ...` with exit 4.

**Not shown:** anything on real hardware; behaviour of any mode after it is entered; flying a mission (AUTO with a mission, takeoff, waypoints); geofence, rally points and other mission types; parameters on any vehicle but the Copter simulator (the code is vehicle-agnostic for parameters and missions, but only this one was run); writing parameters that need a reboot to take effect; one run per attempt. The mode sweep depends on this snapshot's `mode.h` (a firmware with other modes needs the table regenerated).

## What this does and does not show

- Shown: for those twelve simulated frames (and the helicopter's refusal), the plan the prototype derives from the vehicle's own parameters moves exactly the predicted outputs, in the predicted order, with the prototype's own ACK handling.
- Not shown: any other frame (the earlier sweeps cover more), any flight, any real autopilot or motor, any GUI, calibration, parameter editing, mission or map function. Plane, Blimp, tracker and scripted matrices are explicitly unsupported and the helicopter has no motor test to plan. Every generated copter layout and the three scripted example frames were run once; two remapped-output cases were run once. Not shown: a motor with no output at all, scripted frames other than the six examples, and anything on real hardware. The unit-test orders and the integration orders come from the same earlier sweeps, so a shared misreading would not be caught by either.
- The check `moved` uses a 20 microsecond change threshold on `SERVO_OUTPUT_RAW` and ignores outputs that are not motor, throttle, tilt or steering functions; a failure to move something outside that set is not detected.
- The motor test spins motors. It was run against simulators only and must not be run with propellers fitted or against a real aircraft.
