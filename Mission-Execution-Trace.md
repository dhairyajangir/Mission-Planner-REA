# Copter mission execution trace

Scope: static analysis of ArduPilot commit `72b238201f5ea3b556e3809b2ec704fcf701474a` from the supplied archive. Mission upload and readback were exercised separately; this trace does not establish execution of a full mission.

`ArduCopter/mode_auto.cpp:24` initializes Auto mode. It checks whether a mission is present unless checks are ignored and, if the vehicle is armed and landed, rejects the mode change when the mission does not start with a takeoff command. The controller initializes navigation state and marks the mission as waiting to start. This is one entry path; other mode-entry checks also apply.

`ModeAuto::run` at `:91` waits for an AHRS origin before invoking `mission.start_or_resume()`, which chooses behavior using the mission restart configuration. While running, a detected mission change can restart an active waypoint or spline command. Otherwise the method invokes `mission.update()` and then runs the controller for the active Auto submode, including takeoff, waypoint and landing submodes. `ModeAuto::exit` at `:77` stops a running mission when leaving Auto.

`libraries/AP_Mission/AP_Mission.cpp:109` implements `start`: it marks the mission running, resets execution and jump tracking, and advances to the first navigation command; if it cannot advance, it marks the mission complete. `stop` changes the mission state to stopped. `resume` can restart from the beginning if the mission completed, the current navigation index is invalid, or the current command cannot be read from storage. Other resume behavior depends on state and configuration.

`AP_Mission::update` at `:310` returns if the mission is not running or has no commands. It handles mission-change tracking, records the current waypoint for watchdog recovery, and advances or verifies navigation commands. It separately advances or verifies active do-commands. Command-specific callbacks and the actual flight controllers determine what completion means; the source does not imply that every command behaves like a waypoint.

The existing tests prove a two-item mission could be uploaded and read back through the original Mission Planner library and the source-built Copter simulator. They also show separate GUIDED takeoff and LAND behavior with a standalone client.

A further standalone-client run uploaded a four-item home, takeoff, nearby waypoint and land mission to a fresh source-built Copter simulator. It set `AUTO_OPTIONS=2` in that disposable instance to allow Auto takeoff without raising throttle; normal arming checks remained enabled. The upload was accepted, the vehicle entered Auto, reported mission-current sequences 1, 2 and 3 and reached 5.065 metres relative altitude. Status messages reported takeoff, waypoint and land; the harness received reached notifications for items 1 and 2, then a disarmed heartbeat. The result and status messages are in `sitl-evidence/archive-copter-auto-mission/results.json`. The harness did not observe a mission-complete notification or independently check touchdown position; it also recorded a subsequent `Mission: 1 Takeoff` status message, whose cause has not been investigated. This test does not establish GUI behavior, pause/resume, command failures or interrupted execution.

An initial pause/resume test selected mission sequence 2, switched from AUTO to LOITER for five seconds and then requested AUTO with `MIS_RESTART=0`. The reported mission sequence remained 2 during the pause, but the simulator reported ground contact before the return to AUTO; it rejected AUTO with `Auto: Missing Takeoff Cmd` and disarmed. The test did not retain altitude samples during the pause, so the cause of descent is not established. The source LOITER mode obtains a pilot-requested climb rate (`mode_loiter.cpp:94`); that is a possible factor, not a confirmed diagnosis. The failed run remains in `sitl-evidence/archive-copter-mission-resume/`. A separate retry uses BRAKE and records altitude, rather than replacing the first result.

Another separate retry used LOITER with a simulated RC channel-3 override refreshed at 1500 PWM during the pause. It confirmed sequence 2 and 5.065 m relative altitude before entering LOITER. During the pause, 20 `RC_CHANNELS` samples reported channel 3 at 1500 and 21 altitude samples ranged from 4.961 to 5.061 m. Sequence 2 remained reported; after the test released the override and requested AUTO, the mission resumed, reached item 2, progressed to item 3 and later reported disarmed (`sitl-evidence/archive-copter-mission-loiter-centered/results.json`). The earlier failed run did not record its throttle input or pause altitude, and this retry also added an altitude precondition. The comparison therefore does not prove why the first run descended. It tests one simulated mission and RC override, not real radio input or a physical aircraft.

The BRAKE retry confirmed `MIS_RESTART=0` and uploaded a home, takeoff, distant waypoint and land mission. It selected sequence 2 at a reported 5.067 m relative altitude, switched to BRAKE for roughly five seconds, and recorded sequence 2 throughout that interval. The 21 recorded altitude samples during BRAKE ranged from 4.958 to 5.059 m. After returning to AUTO, the client observed sequence 2, a reached notification for item 2, sequence 3, and eventually a disarmed heartbeat. Results and event records are in `sitl-evidence/archive-copter-mission-resume-2/results.json`. After sequence 3, the stream also contained sequence 1 and the status `Mission: 1 Takeoff` near the end of the run; their cause was not established. This is one standalone-client simulation, not a Mission Planner UI test, a full mission-completion proof, or evidence for `MIS_RESTART=1`.

The source's `AP_Mission::resume` (`libraries/AP_Mission/AP_Mission.cpp:130`) can restart the active navigation or do command, while completed missions and invalid or unreadable active commands may restart from the beginning. `start_or_resume` at `:249` chooses between starting and resuming according to configuration and its force-resume flag. The observed sequence is consistent with the selected resume setting but does not independently prove every internal branch.

A separate run repeated the BRAKE interruption with `MIS_RESTART=1`. The vehicle selected waypoint sequence 2, entered BRAKE, then returned to AUTO. Immediately after the AUTO request the captured status stream reported `Mission: 1 Takeoff` and a reached notification for item 1, followed by `Mission: 2 WP`; later it reached item 2, entered the land item and reported disarmed. The first sampled `MISSION_CURRENT` after AUTO was already sequence 2, so that message stream alone did not show sequence 1. The full events are in `sitl-evidence/archive-copter-mission-restart/results.json`. This supports restart behavior for this one already-airborne mission and does not establish all restart, jump-counter, command or flight-state cases.

## Sequence reset after landing

A further `MIS_RESTART=0` mission run recorded heartbeat mode, arming state, status messages and mission sequence through landing and for five seconds after the first disarmed heartbeat. It reported `Disarming motors`, then `Mission: 1 Takeoff`, followed by a disarmed heartbeat still in AUTO. Five further heartbeats remained disarmed in AUTO, and sequence 1 continued to be reported. The harness issued no new mission or arm command after disarm. This status message therefore does not, by itself, show a new takeoff or rearming. The result and complete event stream are in `sitl-evidence/archive-copter-mission-disarm-observe/results.json`.

The verified source snapshot provides a plausible path for this ordering. `AP_Arming_Copter.cpp:826` resets the mission during disarm. `AP_Mission::reset` clears the active command index and loaded flags without assigning the mission state (`AP_Mission.cpp:260`). AUTO's run loop calls `mission.update()` (`mode_auto.cpp:91`); if the mission is still running, an update with no active navigation command advances from the first mission command (`AP_Mission.cpp:310`, `:2157`). `start_command` sends the `Mission: ...` status before its command dispatch (`:405`). This is an inference consistent with the recorded ordering, not proof that those internal conditions occurred: the run did not instrument the mission state or command callback. It also does not explain every post-landing sequence report or establish mission-completion behavior.
