# Log workflow trace

This is a source trace of Mission Planner 1.3.83 and selected simulator-library tests. It does not establish full log handling or screen behavior.

## Source paths

- `mission-planner-1.3.83-source/MainV2.cs:1584` creates a timestamped `.tlog` on connection using `FileMode.CreateNew`. The MAVLink interface writes packet data to its configured log streams (`ExtLibs/ArduPilot/Mavlink/MAVLinkInterface.cs:5343` and nearby code).
- `GCSViews/FlightData.cs` contains log selection, playback and browsing paths. The telemetry log filter includes `.tlog` and `.mavlog` (`:1283`); `LoadLogFile` starts a log playback path. Source-level reachability is not an end-to-end UI test.
- `Log/LogDownloadMavLink.cs:80` calls `GetLogList`, and `:196` calls `GetLog` for a selected log. The communication implementation sends `LOG_REQUEST_LIST` and `LOG_REQUEST_DATA` (`MAVLinkInterface.cs:6232` and `:6009`) and contains retry and error handling.
- `ExtLibs/Utilities/BinaryLog.cs:89` defines `ConvertBin`, used by log-viewing or conversion paths such as `FlightData.cs:1317`. Log browsing and format handling also appear in `Log/LogBrowse.cs`.

## Observed simulator-library test

Using the original Mission Planner 1.3.83 communication assemblies and application binding configuration, a separate harness connected to a fresh ArduCopter 4.7.2 SITL instance and called `GetLogList`. It returned an empty list (`LOG_LIST_COUNT=0`); the transcript is `sitl-evidence/log-list-probe/library-list.log`.

The same library then connected to the locally built 4.8.0-dev simulator with `LOG_DISARMED` enabled. It returned one log entry, ID 1, size 1,183,744 bytes at the time of the list response (`sitl-evidence/nonempty-log-probe/library-list-2.log`). The first download attempt stopped before transfer because the library refused to set an uncached `LOG_DISARMED` parameter (`download-attempt.log`). A second reached `GetLog` but timed out after retries (`download-attempt-2.log`). The harness had not started the separate packet reader used by the application (`MainV2.cs:3035`); `GetLog` queues packet events rather than reading the connection itself.

With a packet reader added to the harness, a third attempt downloaded the earlier, closed log (`download-attempt-3.log`). The 5,660,672-byte download and simulator file have the same SHA-256, `80f2d22edb979b0e9fc219da3c2dbc3a0ff4b86a7d8611728276bc5732041d6d`. A separate pymavlink parser read 140,847 records (`download-verification.json`). The source file had grown between the initial list and simulator shutdown, so its final size exceeds the earlier list response. This verifies one library download and an independent parse; the separate conversion test is described below. Playback, graphing, logging while flying and GUI behavior remain untested.

The original Mission Planner utility DLL's `BinaryLog.ConvertBin` produced an 8,267,692-byte text file from that downloaded log (`conversion-attempt.log`). It reported `Bad Binary log line 119`. The text contains 140,847 lines, equal to the pymavlink record count, but a name-count comparison found 2,565 `MAG` lines versus pymavlink's 2,564 and 38 `UNIT` lines versus pymavlink's 39 (`conversion-verification.json`). A direct sequence comparison first differs at record 1,664 and reports 108,599 positional differences (`sequence-comparison.json`); an insertion or omission can shift many later comparisons, so this does not establish 108,599 independent errors. Heuristic type-name alignment suggests one missing `UNIT` and one extra `MAG` line at the end (`sequence-alignment.json`); repeated types can make alignment ambiguous.

Comparing `UNIT` identifiers isolates ID 45, whose label is empty in the pymavlink parse (`unit-id-comparison.json`). The log's format identifies message 119 as `UNIT` with a `Z` field. In the 1.3.83 source, `BinaryLog.cs:564` decodes `Z` to a byte array, and `:164` trims nulls then uses `Aggregate` without a seed to escape the decoded string. An empty sequence would throw, and `:205` catches exceptions and reports the bad-line warning. This is a source-supported explanation for the missing record, but the catch does not record the exception, so the actual exception was not observed.

A small reproduction extracted the `FMT` record and the empty-label `UNIT` record from the captured log. The original utility DLL emitted the format line, reported `Bad Binary log line 119`, and omitted the UNIT line while returning exit code zero. A synthetic control differing by one byte, with label `x`, produced both lines without that warning. The fixture hashes, outputs and source offsets are in `sitl-evidence/nonempty-log-probe/empty-unit-reproduction.json`. This isolates the behavior to the empty-label fixture for this DLL; the swallowed exception itself remains unobserved.

REA's support-library index identifies `MissionPlanner.Utilities.BinaryLog.ReadMessage` in the distributed `MissionPlanner.Utilities.dll` at method token `0x060002c0` with a method body present. That member identity does not by itself prove source-to-binary equivalence.

The last `MAG` header in the binary is at byte offset 5,660,641, with 31 bytes remaining; the log's `FMT` record specifies 35 bytes for `MAG`. The converter's source at `BinaryLog.cs:472` allocates a zero-filled message buffer and does not check the number of bytes returned by `Read`. A fixture containing that format and partial record produced the same MAG line as a control with four zero bytes appended (`truncated-mag-reproduction.json`). This reproduces the extra output for this truncated record and is consistent with the source path. The exact control flow was not instrumented, and field-level agreement elsewhere remains unverified. The conversion ran through a harness, not the GUI.

## Log-browser observation

The modified, plugin-disabled application copy opened the captured `downloaded.bin` in its Log Browser. Selecting `GPS` → instance `0` → `Alt` displayed a plotted line rising from roughly 578 to 584 metres; the app log records `GraphItem: GPS Alt 0` and `Graphing GPS - Alt` (`sitl-evidence/isolated-log-browser/application-stdout.log`). A separate pymavlink parse found 391 GPS instance-0 samples ranging from 578.12 to 584.09 metres, with the last at 584.09 (`gps-altitude-summary.json`). This checks that the visible range is consistent with one independent summary, not that every plotted point or timestamp is correct. The screenshot was inspected through computer use and was not saved as a separate file. The test did not exercise log playback, export or the unmodified app.

## Telemetry-log truncated-record test

A standalone harness called the distributed `MissionPlanner.ArduPilot.dll` playback methods on local `.tlog` fixtures made from the first heartbeat in a previously recorded simulator log. The original complete 25-byte record produced a 17-byte MAVLink packet. Removing one or four trailing bytes caused the private reader, invoked separately through reflection, to return a 17-byte buffer with zero-filled missing bytes. The public `readPacket()` rejected both of those fixtures with checksum failures. Flipping the checksum in the intact record was also rejected. The fixtures, source-log hash and outputs are in `sitl-evidence/tlog-playback-probe/`.

A crafted control changed heartbeat payload bytes and used an independently calculated X.25 checksum whose final byte was zero. Both the complete control and a copy missing that final byte returned the same 17-byte packet from the public `readPacket()`; the truncated file had 24 bytes versus 25 for the control. This shows that a checksum match does not establish the record was complete for this specific fixture. It does not establish how often this occurs in real logs, or GUI playback behavior. The source at `MAVLinkInterface.cs:6630` does not use the byte count returned by the read into the packet buffer; checksum validation follows at `:5001`. The source and binary were not proven identical builds, but this path is consistent with the observed harness result.

## Telemetry-log recovery tests

Sequential `readPacket()` calls against two complete heartbeat records returned both packets. When the first record had a flipped checksum, the first call returned an invalid message and the next call returned the intact second packet. In another fixture, three non-framing bytes inserted between the first timestamp and its frame were skipped; both the resynchronized first packet and the next packet were returned. When only those three noise bytes followed the timestamp and the file ended, the library logged `EndOfStreamException` internally and returned an invalid message at end of file. Fixture bytes and the complete harness output are in `sitl-evidence/tlog-recovery-probe/`.

These tests used one MAVLink 1 heartbeat and a standalone harness, not the GUI. They establish recovery for the specific corruptions and record boundaries above; they do not establish recovery for arbitrary corruption, timestamps, signed frames or partial multi-packet streams.

## Telemetry-log timestamps

The source reader treats the first eight bytes of a normal record as a big-endian Unix timestamp in microseconds, converts it to whole milliseconds, and updates `lastlogread` (`MAVLinkInterface.cs:6503–6553`). For a `.rlog` file it skips timestamp reading; for another extension it also rewinds if the first byte of the presumed timestamp is a MAVLink framing byte. The Flight Data playback loop calculates a delay from successive `lastlogread` values, sets negative intervals or intervals over 9,999 ms to zero, divides by the playback-speed setting, and applies further timing adjustment (`FlightData.cs:3412–3469`). These are source observations, not measured GUI timing.

A standalone library harness read two synthetic heartbeat records with timestamps `1600000000123456` and `1600000001124690` microseconds since the Unix epoch. It reported UTC times `2020-09-13T12:26:40.123Z` and `2020-09-13T12:26:41.124Z`, consistent with truncation to milliseconds. Reversing the two timestamps made the reported time move backward; the reader did not reject the packets. Two raw frames saved as `.rlog`, and the identical bytes saved as `.tlog`, were both read as two packets with `lastlogread` left at its default value in this fresh harness. Inputs and outputs are in `sitl-evidence/tlog-timestamp-probe/`. These observations do not verify speed controls or timing in the desktop UI.

## Signed-frame playback

The source explicitly excludes log playback from the signature verification branch (`MAVLinkInterface.cs:5057–5062`), while its preceding CRC check applies to the packet. In a standalone test, two synthetic MAVLink 2 heartbeat records had the signed flag set and identical valid CRCs, but different arbitrary 13-byte signature blocks: all zeros and all `0x55`. The public playback reader returned both packets. A third fixture changed one payload byte without changing its CRC; the reader rejected it. Inputs and output are in `sitl-evidence/tlog-signature-probe/`.

The synthetic signature blocks were not generated from a signing key. This shows the observed playback behavior, not whether either block is cryptographically valid. It does not test live-link signing, key handling, replay protection or GUI playback, and should not be generalized to those paths.
