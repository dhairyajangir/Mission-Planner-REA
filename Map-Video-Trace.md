# Map and video source trace

Scope: selected static paths in upstream Mission Planner 1.3.83, plus the limited local tests described below. Online map providers, real video sources and physical cameras have not been verified.

## Maps

`GCSViews/FlightPlanner.cs:150` sets the planner map's cache location under `Settings.GetDataDirectory()`. The same view populates its map-type selector from `GMapProviders.List` at `:176`. The selection handler around `:2224` assigns the selected provider to the planner map and, when applicable, the Flight Data map. Provider-specific branches and credentials must be inspected before assuming that every listed provider works.

`GCSViews/FlightData.cs:359` also assigns a cache location under the data directory. `MainV2.cs:1989` changes GMap cache settings during application shutdown. Other source paths request tile downloads or write custom tiles to the cache; the existence of these calls does not establish offline coverage, current service availability, licensing or cache integrity.

`Program.cs:319` assigns `MissionPlanner.Maps.MyImageCache` as the primary cache. Its source constructs a provider/zoom/Y/X file path and writes using `File.OpenWrite` (`ExtLibs/Maps/MyImageCache.cs`). A local harness called the distributed cache library using a synthetic ASCII payload and a workspace path, with the test copy's redirected utility library. It stored and found a 24-byte payload and reported a neighboring key absent. When the same key was overwritten with one byte, the resulting file remained 24 bytes and contained `xffline-cache-fixture-v1` (`sitl-evidence/map-cache-probe/probe.log`). This agrees with `File.OpenWrite` retaining an existing file's tail when fewer bytes are written. The fixture was not an image and the harness did not test image decoding, map rendering, a provider download or every cache scenario. The harness's explicitly supplied path lacked a trailing separator, so its test directory is named `cacheTileDBv3`; this should not be generalized to the normal app cache path.

A separate local harness stored a synthetic 2×2 PNG in a fresh cache and retrieved it through `GetImageFromCache`. The distributed cache/image code returned a 2×2 image with the expected red pixel (`sitl-evidence/map-decode-probe/probe.log`). This verifies one synthetic image decode using the test copy's redirected data path; it does not verify stale-tail image behavior, map rendering, an online provider, or offline coverage of a real area.

The `MissionPlanner.Maps.dll`, `GMap.NET.Core.dll` and `GMap.NET.Drawing.dll` files in the test copy matched their portable-distribution counterparts by SHA-256. The utility DLL used to select the data path was modified, so this is not an unmodified whole-application test.

## Video

`GCSViews/FlightData.cs:45` constructs a GStreamer wrapper. Its source-selection handler at `:4749` saves a pipeline string, checks for GStreamer and starts the wrapper. A separate HereLink handler constructs an RTSP pipeline at `:3091`. `MainV2.cs:3340` also handles discovered video streams, and `:3405` receives image events and updates the HUD background. There are other video paths in the source; this is not an exhaustive inventory.

`ExtLibs/Utilities/GStreamer.cs:1184` stops the previous worker and starts a background thread. The thread initializes GStreamer through native bindings, parses the supplied pipeline, looks for an appsink named `outsink` and starts the pipeline. If an appsink is present, it configures a one-buffer limit and frame dropping. `Stop` at `:1490` signals the worker and joins it. Dependency errors, platform-specific native libraries, stream failure, shutdown timing and frame delivery need runtime tests.

The REA support-library index identifies `MissionPlanner.Utilities.GStreamer.Start` and `Stop` in the distributed `MissionPlanner.Utilities.dll` at method tokens `0x060004de` and `0x060004eb`. These are binary member identities; they do not by themselves prove that every behavior in the source trace matches the release binary.

The separate `CaptureMJPEG` path reads multipart HTTP frames and raises image events (`ExtLibs/Utilities/CaptureMJPEG.cs:13`); `MainV2.cs:3452` subscribes to those events. A standalone harness using the portable distribution's utility and drawing libraries connected to a local HTTP server serving three synthetic 16×16 JPEGs. It received three image events with red, green and blue center pixels, called `Stop`, and observed a subsequent null-image event (`sitl-evidence/mjpeg-capture-probe/`). The source-built harness required the application's binding redirects; its compiler warned that the drawing library referenced an older SkiaSharp version than the bundled DLL. This tests one local multipart stream and stop sequence, not HUD rendering, GStreamer, stream reconnection, a real camera or deployment compatibility.

A second local server sent a first multipart image without `Content-Length`, then served a valid stream on the next connection. The reader logged `KeyNotFoundException`, emitted a null-image event, reconnected, and delivered three colored frames; after `Stop` it emitted another null-image event (`sitl-evidence/mjpeg-missing-length/`). This exercises one missing-header case and one successful reconnection, not other malformed streams or network failures.

A later application test served a labeled, multicolored 640×480 synthetic MJPEG fixture from localhost. The modified, plugin-disabled test copy's script observed a 640×480 HUD background, and the displayed HUD visibly showed the fixture's colored regions beneath the instrument overlay. The script then called `Stop` and recorded the HUD background as cleared. The screenshot was inspected but not saved (`sitl-evidence/mjpeg-hud-ui-2/`). A first run could not connect to localhost because of sandbox socket restrictions (`mjpeg-hud-ui/`). In the second run Windows displayed a firewall permission prompt; no permission was granted. After the stream had stopped, the system prompt obstructed the app's close control, so the test-only process was terminated and its launcher recorded exit code 1. This verifies one observed rendering in the patched copy, not a normal installation, camera, GStreamer, or a clean application shutdown.

Three further standalone runs served a JPEG body 50 bytes shorter than its declared `Content-Length` and closed the connection. In each, no image or clear event arrived and the reader thread was still alive 1.5 seconds after `Stop` (`sitl-evidence/mjpeg-truncated-body/`, `mjpeg-truncated-body-2/` and `mjpeg-truncated-body-3/`). In the second and third runs the entire harness process consumed approximately 1,516 milliseconds of CPU during that 1.5-second wait; this is process-wide, not a per-thread measurement. In the third run, a separate background thread called `runAsync` again and did not return within one second. The source loop accepts `Read` returning zero while leaving the remaining length unchanged (`CaptureMJPEG.cs:150`), `Stop` only changes `running` (`:49`), and `runAsync` waits while the previous worker remains alive (`:31`); those paths are consistent with the observations, but no thread stack was captured. These bounded synthetic-stream tests do not establish how often real cameras trigger the behavior, that either thread could never exit, or that the application UI was blocked.

In a separate cache-only UI run, a test script selected OpenStreetMap at zoom 3 and seeded 64 labeled synthetic tiles into the redirected cache. The modified, plugin-disabled application visibly rendered several tiles, including labels for columns 5–7 and rows 3–6. The right part of the viewport remained blank. The screenshot was inspected but not saved. The seed manifest and application status are in `sitl-evidence/offline-map-ui/`; the app exited with code 0. This establishes a limited synthetic-cache rendering observation, not real imagery, complete viewport coverage, online access, or normal unmodified application behavior.
