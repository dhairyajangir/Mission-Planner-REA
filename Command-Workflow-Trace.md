# MAVLink command and acknowledgement trace

This trace concerns Mission Planner 1.3.83's distributed `MissionPlanner.ArduPilot.dll` and a source-built disposable Copter SITL from ArduPilot commit `72b238201f5ea3b556e3809b2ec704fcf701474a`. Source references use the matching-version Mission Planner tag; matching labels alone do not prove a bit-identical build.

## Source path

`MAVLinkInterface.doCommand` and `doCommandAsync` (`ExtLibs/ArduPilot/Mavlink/MAVLinkInterface.cs:2677`) send `COMMAND_LONG`. When an acknowledgement is required, the normal path waits two seconds, retries up to three times with an incremented confirmation field, and accepts `COMMAND_ACK` only from the requested system and component with the same command ID. `ACCEPTED` returns true; `IN_PROGRESS` resets the wait and disables further retries; other result values return false. A timeout throws. Calibration, reboot, arming, home-position and no-ack cases have separate source branches. Full accelerometer calibration was separately tested: its special branch returns true without waiting for the ACK, including in an armed-SITL case where the vehicle later sent `FAILED`; see `Accelerometer-Calibration-Trace.md`. The other special branches are not covered by the command runtime tests below.

REA's static index identifies `doCommandAsync` as method token `0x06000462` and its generated state-machine `MoveNext` as `0x060007f2`; `doCommandIntAsync` is `0x06000464` and its `MoveNext` is `0x060007f4`. `mission-planner-binary-evidence/command-method-map.json` records the distributed DLL hash, IL hashes and static call references. These tokens are specific to that assembly build and do not establish runtime dispatch.

In the pinned ArduPilot source, `GCS_Common.cpp:5867` dispatches `MAV_CMD_GET_MESSAGE_INTERVAL` to `handle_command_get_message_interval` (`:3351`). That handler reports the requested message interval and returns a MAVLink result; the command is read-only in this test.

## Acknowledgement loss tests

The original library sent `GET_MESSAGE_INTERVAL` for `ATTITUDE` (message ID 30) to system/component 1:1 through a local frame-aware relay. Three independent disposable SITL runs used normal delivery, dropped the first matching acknowledgement, or dropped every matching acknowledgement. The relay reconstructed MAVLink frames, forwarded unrelated traffic, and retained the original and forwarded streams plus dropped packets. A separate pymavlink decoder checked the saved frames and hashes (`research-tools/summarize-command-ack.py`).

| Relay condition | Requests observed, confirmation fields | SITL acknowledgements accepted by relay | Forwarded to library | Library result |
| --- | --- | --- | --- | --- |
| Normal | 0 | 1 accepted | 1 | `True` |
| First acknowledgement dropped | 0, 1 | 2 accepted | 1 | `True` |
| All matching acknowledgements dropped | 0, 1, 2, 3 | 4 accepted | 0 | `Timeout on read - doCommand` |

The simulator's accepted acknowledgements show receipt and acceptance of each read-only request, including repetitions. The all-loss timeout does not mean the simulator rejected the command; it means the library did not receive a matching acknowledgement. This test does not prove that retrying an arbitrary state-changing command is safe or idempotent.

Evidence is under `sitl-evidence/command-ack-normal/`, `command-ack-drop_one/` and `command-ack-drop_all/`; each has `summary.json`, the library log, relay log and raw captures. The independent decoder reported 164 bad-data fragments in each initial downlink, corresponding to bytes outside successfully decoded MAVLink frames; the relay recorded and forwarded those stray bytes. No physical aircraft or full UI was used.

The same read-only request was separately sent as `COMMAND_INT` in three new SITL runs (`sitl-evidence/command-int-ack-normal/`, `command-int-ack-drop_one/` and `command-int-ack-drop_all/`). With normal delivery, one request succeeded. With the first ACK dropped, two requests were observed and the library returned true. With all four ACKs dropped, four requests were observed and the library timed out. The independently decoded requests had frame 0, target 1:1, `param1=30` and zero x/y coordinates; all four observed ACKs in the all-loss run reported `ACCEPTED`. The capture decoder again counted 164 non-decoded fragments in each initial downlink. `COMMAND_INT` has no confirmation field in this fixture, so retries are counted by complete decoded request frames.

A separate SITL run sent command ID 65530, absent from the local pymavlink dialect, once in each form. The captured simulator ACKs both had result `UNSUPPORTED` (3), and both library methods returned false. Evidence: `sitl-evidence/command-unsupported-normal/summary.json`. The preserved `relay-result.json` scope string incorrectly describes an interval request; the summary records that mistake and the actual decoded command. The relay did not deliberately drop ACKs in this run.

## Synthetic acknowledgement filtering

The distributed library was also exercised with in-memory MAVLink 1 packets, without a vehicle or socket. For each of three cases, an `ACCEPTED` ACK from the wrong system, wrong component or wrong command was followed by a correctly addressed `DENIED` ACK. The library consumed both and returned false. A correctly addressed `IN_PROGRESS` followed by `ACCEPTED` returned true; a single `DENIED` returned false. With `requireack=false`, the method returned true while a queued ACK remained unread. The fixture does not establish transmission or command execution in that no-ack case. All six cases ended with `giveComport=false`.

`sitl-evidence/command-ack-synthetic/summary.json` records the decoded fixtures and library results; `research-tools/summarize-command-ack-synthetic.py` rechecks them.

The same fixtures were then passed to `doCommandInt`. Wrong-system, wrong-component and wrong-command `ACCEPTED` ACKs were skipped before the matching `DENIED`; the method returned false. A matching `IN_PROGRESS` ACK returned false immediately, leaving the later `ACCEPTED` ACK unread. In contrast, `doCommand` consumed both and returned true in the paired fixture. Both methods returned true without reading the queued ACK when `requireack=false`. The `COMMAND_INT` results are in `summary-int.json` and `probe-int.log` in the same evidence folder. These are synthetic method-level observations, not evidence of a vehicle operation or user-visible fault.

In another in-memory fixture with a single `IN_PROGRESS` ACK and no terminal ACK, `doCommand` threw its timeout after an observed 2,510 ms, while `doCommandInt` returned false after an observed 9 ms. Both left `giveComport=false`. These durations describe one run, not timing guarantees. Evidence: `sitl-evidence/command-progress-only/summary.json` and its fixture and log.

Two further local SITL sessions used a relay to insert a synthetic unsigned `IN_PROGRESS` ACK immediately before the simulator's original `ACCEPTED` ACK for the read-only interval request. `doCommand` returned true; `doCommandInt` returned false. The inserted ACK reused the original ACK's sequence number, so this is not a faithful simulation of all real multi-stage acknowledgement sequences. The relay captured and forwarded both ACKs; the amount of data left in the TCP buffer after the call also included unrelated traffic and does not by itself identify an unread ACK. Independent frame checks and logs are in `sitl-evidence/command-progress-live-long/summary.json` and `command-progress-live-int/summary.json`. This is a controlled relay observation, not a demonstrated user-visible failure or signed-link test.

The experiment was repeated with consecutive ACK sequence numbers. The relay inserted `IN_PROGRESS` at the simulator ACK's original sequence, then changed the simulator's `ACCEPTED` ACK to the next sequence and recalculated its checksum. The long method again returned true and the int method returned false (`command-progress-sequential-long/summary.json`, `command-progress-sequential-int/summary.json`). Subsequent telemetry sequence numbers were not adjusted, so the entire forwarded stream was not sequence-normalized. Both ACKs were unsigned and the progress ACK was synthetic.

In a third consecutive-sequence `COMMAND_INT` run, the harness read the available TCP bytes after the method returned false. Independent decoding found the complete shifted `ACCEPTED` ACK among those 120 bytes, confirming it was unread by the command method at that point (`command-progress-drain-int/summary.json`). The harness deliberately drained the transport; a full application's separate reader was not running, so this does not establish whether or when that reader would process the ACK.

Another controlled run sent two identical read-only `COMMAND_INT` requests. For the first, the relay inserted `IN_PROGRESS` and forwarded a sequence-adjusted `ACCEPTED` ACK; the library returned false. The harness waited 500 ms, then sent the second request. The relay observed the second request and dropped its simulator ACK, yet the second library call returned true. The captured downlink contains only the earlier progress and accepted ACKs for this command; the new ACK is in the dropped capture. The test therefore shows an earlier matching ACK satisfying the later call in this isolated sequence. See `sitl-evidence/command-stale-ack-int/summary.json`. The test used an unsigned synthetic progress ACK, a deliberately altered relay and two identical read-only requests; it does not establish a failure in the full application or with a physical vehicle.

The source ACK filter compares sender system/component and command ID but does not compare the MAVLink 2 ACK target extensions. In a separate in-memory test, an `ACCEPTED` ACK from 1:1 for command 510 carried target 42:17, followed by a `DENIED` ACK from 1:1 for the same command carrying target 255:190. Both command methods returned true after the first packet and left the second unread. Controls returned false for a single 255:190-targeted `DENIED` ACK and true for an `ACCEPTED` ACK with zero target fields. See `sitl-evidence/command-ack-target-synthetic/summary.json`.

Two further disposable-SITL runs tested the same target-field condition through an actual local TCP session, one for each command form. The library's request was from 255:190 to 1:1. The test relay replaced the simulator's unsigned `ACCEPTED` ACK target 255:190 with 42:17, recomputed the MAVLink checksum and forwarded it; sender, sequence, command and result remained the same. Both methods returned true. Independent decoding verified the original and modified ACKs and the captured request (`sitl-evidence/command-target-live-long/summary.json` and `command-target-live-int/summary.json`). The only changed byte positions were the two target bytes and checksum. This is a deliberately modified local relay test, not proof of an attack, signed-link behavior or a user-visible failure.

These tests do not cover real-vehicle `IN_PROGRESS` handling, delayed or duplicated valid ACKs, all MAVLink result codes, other `COMMAND_INT` commands or frames, automatic UI behavior or commands with side effects.
