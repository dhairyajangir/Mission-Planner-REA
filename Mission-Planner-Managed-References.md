# Mission Planner managed assembly references

The Mission Planner 1.3.83 portable distribution contained 260 files previously identified as managed PE candidates. REA's static managed-artifact inspection completed for all 260, with a hash recorded for each input and an individual result under `mission-planner-binary-evidence/managed-references/`. The resulting `managed-reference-graph.sqlite` indexes 260 assembly identities and 1,063 declared assembly references.

The index matches declarations to bundled assembly identities by name, version, culture and public-key token. Of the 1,063 declarations, 402 have one exact candidate in this inventory and 661 have none; 71 of the latter have at least one bundled assembly with the same name but a different identity. No declaration has multiple exact candidates in this set. Frequent names among declarations without an exact bundled candidate include `mscorlib` (168 declarations), `netstandard` (91), `System` (78), and `System.Core` (50). These are counts of declarations, not counts of distinct missing files or confirmed faults.

The database has `assemblies`, `assembly_references` and `exact_candidates` tables. Each assembly row links its portable-distribution path, SHA-256 and REA evidence file. `research-tools/build-managed-reference-graph.py` refuses to construct a complete index if the 260-file inspection is unfinished or input hashes differ. The summary and SQLite digest are in `mission-planner-binary-evidence/managed-reference-graph-summary.json`.

These are static identity comparisons. They do not apply `.config` binding redirects, simulate .NET probing, test the installed framework or global assembly cache, resolve native libraries, or discover assemblies loaded dynamically. Therefore an absent exact candidate is not proof of a broken installation, and a matching candidate is not proof that it will load successfully. Runtime dependency behavior and individual library functionality remain open.

For example, twelve declarations request `System.Memory` version `4.0.1.1`; the portable files contain version `4.0.1.2`. The application's configuration declares a redirect covering versions up to `4.0.1.2` to that version (`mission-planner-portable/MissionPlanner.exe.config:138`). The file's public-key token matches the configuration entry. This explains why an exact-identity-only index is insufficient for that case; the index does not establish that the redirect is applied in any particular runtime context.

Member-level REA evidence is separately indexed for 30 selected support assemblies: 14 in `rea-supporting-index.sqlite` and 16 in `rea-extended-index.sqlite`. The extended index adds eight plugin-directory assemblies and eight root-level device, firmware, video or utility binaries, including `DroneCAN.dll`, `px4uploader.dll`, `WebCamService.dll` and `Updater.exe`. It contains 845 type rows, 5,112 method rows and 22,934 call-site rows; its per-file hashes and REA results are in `extended-assembly-members/manifest.json`. Call-site rows are static IL references, not evidence of execution or a complete runtime call graph. Other managed files still lack member-level indexing.

An additional scan of the other 229 managed files is recorded in `remaining-managed-members/manifest.json`: 216 individual results are complete and 13 partial. Some large files report partial coverage because REA reached its 64 MiB metadata-representation limit; a partial result is not evidence that unreported methods are absent. For `Accord.Statistics.dll`, the partial whole-assembly REA result's 680 type tokens matched an independently generated Mono.Cecil type inventory. Subsequent targeted REA batches recovered all 679 non-module types and 7,812 method records against the independent counts, including per-type counts. These are indexed in `accord-statistics-batches/index.sqlite` with 19,782 static call sites; its summary records hashes of the batch manifest and coverage comparison. Matching metadata counts does not establish runtime behavior or prove that every call can be resolved.

The same method recovered all 59 non-module types and 485 method records in `Accord.Vision.dll`, compared with Cecil metadata. Its separate `accord-vision-batches/index.sqlite` contains 24,838 static call sites. Batches can be reproduced for other root-level assemblies using `prepare-cecil-type-inventory.py`, `inventory-accord-statistics-batches.py`, `summarize-accord-statistics-coverage.py`, and `build-accord-statistics-index.py`, each with the assembly filename as an argument. The index builder refuses incomplete token coverage by default; its explicit `--allow-partial` option writes a separately named partial index with coverage marked false.

Targeted REA batches also recovered all 1,371 non-module types and 7,542 method records in `System.Reactive.dll`, matching independent Cecil counts per type. The separate `system-reactive-batches/index.sqlite` contains 28,385 static call sites. These are static records and do not establish runtime execution.

For `IronPython.dll`, targeted REA batches recovered 1,203 non-module types and 12,860 methods, matching independent per-type metadata counts. `ironpython-batches/index.sqlite` records 55,286 static call sites; no IronPython script execution was tested by this inventory.

For `SixLabors.ImageSharp.dll`, targeted REA batches recovered 1,500 non-module types and 11,272 methods, matching independent per-type metadata counts. `sixlabors-imagesharp-batches/index.sqlite` records 45,132 static call sites. These records do not prove image-decoding behavior.

For `alglibnet.dll`, targeted REA batches recovered 368 non-module types and 5,814 methods, matching independent per-type metadata counts. `alglibnet-batches/index.sqlite` records 31,470 static call sites; no numerical behavior is established by this inventory.

For `Xamarin.Forms.Core.dll`, targeted REA batches recovered 1,262 non-module types and 9,303 methods, matching independent per-type metadata counts. `xamarin-forms-core-batches/index.sqlite` records 29,850 static call sites. This is not a runtime test of Xamarin controls.

For `OpenTK.dll`, targeted REA batches recovered 3,857 of 3,869 non-module types and 22,053 of 33,436 methods. Two bare nested-type selections, `Ext` and `NV`, exceeded REA's 64 MiB metadata-representation limit; each name selects multiple nested types, leaving 12 type tokens without complete REA records. `opentk-batches/index-partial.sqlite` contains the completed batches and explicitly marks the index incomplete. A separate Cecil fallback indexed 33,436 method definitions and 23,981 method-reference instructions in `remaining-managed-members/opentk-cecil-index.sqlite`. Cecil is a different static inspection path, not recovered REA coverage, and neither index establishes runtime behavior.

`Accord.Math.Core.dll` remains partial in REA even when selecting just `Accord.Math.Elementwise`; that one type exceeds the same 64 MiB representation limit, and REA's member command exposes type selection rather than method selection. A separate Mono.Cecil fallback recorded all 10,540 method definitions and 32,288 IL instructions whose operand is a method reference in `remaining-managed-members/accord-math-core-cecil-index.sqlite`. The counts match the Cecil type inventory. This fallback is not REA coverage, and its static references include method-reference instructions beyond calls; they do not establish execution or resolve every target.

For `Accord.Math.dll`, targeted REA batches returned 465 of 466 non-module types and 4,954 of 12,532 expected methods; the remaining `Accord.Math.Matrix` type hit the representation limit. The recovered REA batches are searchable in `accord-math-batches/index-partial.sqlite`, with 16,186 static call sites and explicit incomplete coverage in its summary. A separate Cecil index contains 12,532 method definitions and 45,064 method-reference instructions for the assembly. Its scope and limitations are the same as the Cecil fallback above. The batch coverage comparison remains explicitly partial.

`rea-remaining-index.sqlite` is a searchable index of the 216 individually complete results from that scan. Its accompanying `rea-remaining-index-summary.json` identifies the exact manifest snapshot, database hash and 13 excluded partial files. It contains 19,109 types, 139,780 methods and 492,211 static call sites. `research-tools/build-remaining-managed-index.py` rebuilds the snapshot from the manifest; targeted recoveries and the Cecil fallback are stored separately.
# Additional static metadata indexes

The three prior REA gaps were recovered using a separate copy of REA 6.8.0 whose managed representation budget was changed from 64 MiB to 256 MiB. The original tool and its partial evidence remain unchanged. The exact changed CLI file and hashes are recorded in `mission-planner-binary-evidence/rea-raised-budget-modification.json`; the four affected captures are in `rea-raised-budget/`. Combined batches are labeled `original` or `raised-budget` in their manifests. The combined comparisons matched Cecil for `Accord.Math.Core` (2 non-module types, 10,540 methods), `Accord.Math` (466, 12,532) and `OpenTK` (3,869, 33,436). Their separate searchable indexes are under the corresponding `*-mixed-batches/` directories. These comparisons establish matching type tokens and per-type method counts, not equivalence of the modified REA tool or runtime behavior.

For one smaller `AForge.Math.Gaussian` selection, the original and modified REA copies produced identical normalized results and identical captured JSON (`rea-raised-budget/variant-comparison.json`). This is a single control case, not proof that the tools behave identically for larger selections.

## Managed-to-native declarations

REA's `inspect-managed-native-boundaries` pass covered all 260 portable-package managed candidates with complete reported coverage. The saved captures and `managed-native-all/index.sqlite` contain 2,868 P/Invoke declaration rows across 43 assemblies. The separate 11,065 native-implementation boundary rows include those 2,868 P/Invoke methods and 8,197 runtime-provided methods; they are not a count of functions actually called. The index records assembly paths and method tokens, and its summary records hashes and coverage.

`managed-native-all/native-name-matches.sqlite` compares a case-insensitive DLL basename, adding `.dll` when absent, then checks the requested entry-point name against complete bundled native export tables. It contains 2,276 candidate rows, of which 1,190 have an exact export-name match. Multiple architectures and paths produce multiple rows for the same declaration. A missing candidate may be supplied by Windows or another runtime location; an exact name match does not establish architecture compatibility, name decoration or suffix probing, loader selection, function signature compatibility, or execution. This is a static cross-reference, not a runtime binding test.

For example, the recorded x64 `ogr_wrap.dll` exports `CSharp_CreateGeometryFromGML`, while the x86 copy exports `_CSharp_CreateGeometryFromGML@4`. The comparison treats those as different names. That difference alone does not establish whether a Windows runtime can bind either declaration.

An additional REA `verify-managed-native-boundaries` trial supplied the saved `ogr_csharp.dll` boundary record and the x86 and x64 Windows PE export records. REA classified both native records as unsupported input and left all 421 declarations unresolved; its coverage was partial (`managed-native-all/ogr-rea-verification-output.json`). The separate basename/export comparison above is therefore not a successful result from that REA verification operation.

Independent Cecil captures and searchable SQLite indexes now cover three further distributed managed assemblies: `BouncyCastle.Cryptography.dll` (21,095 method definitions; 83,783 method-reference instructions), `Microsoft.CodeAnalysis.dll` (16,043; 46,845), and `Microsoft.CodeAnalysis.CSharp.dll` (37,576; 156,085). Their capture hashes, assembly hashes, index hashes and counts are recorded in the corresponding `*-cecil-index-summary.json` files under `mission-planner-binary-evidence/remaining-managed-members/`. Counts were checked against the separate per-type metadata inventory. These are static definitions and IL references, not evidence that those methods execute or that every call resolves at runtime. Separate REA batch comparisons matched all 2,630 non-module types and 21,095 methods in BouncyCastle, all 1,993 types and 16,043 methods in Microsoft.CodeAnalysis, and all 2,549 types and 37,576 methods in Microsoft.CodeAnalysis.CSharp. Their REA indexes and summaries are in the corresponding `*-batches` directories.
