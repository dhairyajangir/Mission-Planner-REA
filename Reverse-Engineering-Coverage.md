The first Blimp/antenna-tracker build was interrupted and its temporary tree disappeared. A one-worker retry then hit its one-hour timeout during Blimp compilation; its attempt log and status are retained in `sitl-evidence/archive-linux-blimp-retry-build.log` and `archive-linux-extras-retry-build-status.json`. The tree disappeared before a separate resume process could use it. A later attempt built both targets; its status and published hashes are in `archive-linux-extras-retry2-build-status.json`.

The original Mission Planner library also discovered two source-built Copter simulators through a local frame-aware relay, read different values for the same parameter by system ID, switched selected systems and restored the second value. See `Connection-Telemetry-Trace.md` and `sitl-evidence/dual-sitl-library-attempt3/summary.json`. This does not establish behavior with a normal multi-vehicle network, the full UI, concurrent operations or aircraft.

In one disarmed Copter SITL run with telemetry streams enabled, a test-patched Mission Planner Utilities assembly supplied 40 terrain-data blocks from a synthetic flat 321 m HGT tile; the simulator reported 321 m at the requested coordinate with 16 blocks still pending. A separate sloped tile run produced 656 samples matching the independently calculated gradient, and an all-void tile run produced no terrain-data frames while requests remained pending. In another run a relay dropped one terrain block and later delivered a matching retransmission. An earlier run without explicit stream configuration timed out with no captured terrain requests. See `Terrain-Workflow-Trace.md`; these runs do not validate real terrain, full-grid completion or physical navigation.

Original Mission Planner library calls, including the planner's high-level `mav_mission` path, uploaded and read back a typed four-item fence in disarmed Copter SITL while preserving the separately read normal mission. One copied-storage restart returned an error during mission readback; after a fresh upload with pre-shutdown and startup waits, a separate restart read back selected fields for all six items. Legacy fence-point readback completed against prebuilt Copter 4.7.2 but timed out in two runs against the source-built 4.8.0-dev binary. The older candidate source contains a guarded legacy handler, absent from the supplied newer source; the older binary's exact build configuration is unknown. See `Fence-Workflow-Trace.md`; physical persistence, rendered UI and fence enforcement remain unverified.

Separate Copter 4.7.2 SITL runs exercised both conversions between a legacy return point and closed triangle and a typed return point with three inclusion-polygon vertices. A further run added an exclusion circle: legacy fetch timed out after simulator warnings, while selected fields of all five typed items survived the request. Other shapes remain untested.

In a separate 4.7.2 run with that advanced fence, a single legacy return-point write returned true. The following typed read contained only the new return point; the triangle and circle were absent. This simulator result is a compatibility hazard for a custom client that mixes old and typed fence operations; it does not establish behavior across builds or real hardware.

The original Mission Planner MAVFTP and mission packing libraries also transferred a four-item fence to source-built 4.8-dev SITL. Normal mission-protocol and MAVFTP readback matched selected item fields. A first harness without a packet-reading loop recorded FTP retries, returned from `UploadFile` with an empty fence, and failed on a null download; the packet-pumped retry succeeded. In a separate packet-pumped test, a relay dropped all 30 replacement write requests; `UploadFile` returned normally and readback still matched the earlier fence. See `Fence-Workflow-Trace.md`. The planner UI and hardware remain untested.

Further packet-pumped SITL tests dropped the middle FTP write or all 30 final-write acknowledgments. Both calls returned normally; readback matched the old fence in the first case and the replacement in the second. The middle-loss relay dropped fewer frames than intended; two acknowledgment-loss injection attempts also failed before the corrected run. Their captures are retained. See `Fence-Workflow-Trace.md` for exact limits.

Pinned MAVProxy source uploaded a two-item mission in two disarmed SITL runs, one with its final acknowledgment dropped. MAVProxy printed that both waypoints were sent in both runs; a separate client read the waypoint back with matching selected fields. Two earlier quoted-path attempts sent no mission items. See `MAVProxy-Architecture-Trace.md` for capture and home-item differences.

Another MAVProxy SITL run sent an unsupported replacement after a valid baseline. The console printed that both items were sent and then displayed the unsupported acknowledgment; independent readback matched selected baseline fields. This covers one rejected command and does not establish general rollback.

Three disarmed MAVProxy SITL runs tested downstream forwarding of a read-only parameter request. The request passed when forwarding was enabled or the disarmed override was enabled, and did not appear on the captured master link when both were disabled. Two relays recorded connection resets. See `MAVProxy-Architecture-Trace.md`.

Two further MAVProxy SITL retries forced simulated arm and later observed disarm. With only the disarmed override enabled, a downstream parameter request did not reach the captured master link while armed; with `mavfwd=true`, it did. Initial pre-initialization arm attempts failed. This covers one read-only message in simulation, not physical flight or other messages.

The original library started accelerometer calibration in disarmed Copter SITL and received repeated level-position requests. One test sent a wrong position, observed a failed ACK and repeated request, then sent level and observed an accepted ACK and the next request. In another run using SITL's calibration model, all six positions were acknowledged and SITL reported calibration success. After restarting from copied simulator storage, 14 reported accelerometer IDs, offsets and scales matched the values emitted during calibration. Physical sensors and hardware persistence were not tested. See `Accelerometer-Calibration-Trace.md`.

Two forced-armed simulator tests found that the library's full-accelerometer calibration call returned true before the vehicle's failed ACK and disarm notice. Source shows the early return is intentional for this command. Instrumented runs invoked the unrendered control handler directly: its calibration state and `Click when Done` button remained after the rejection, and another invocation sent position 0. A backstage page-switch test reused the control and retained two subscriptions before another start added two; a disposal test found those four still targeted the disposed control before closing the connection. A subsequent instrumented run logged callback exceptions after new simulator packets arrived. A synchronous disarm harness timed out despite a captured ACK, while a comparison using a worker and message pump exited; the cause is not isolated. Normal rendered UI interaction remains untested. Failed attempts are retained in `Accelerometer-Calibration-Trace.md`.

In a controlled two-request `COMMAND_INT` test, an earlier accepted ACK was left queued after a synthetic progress response; the second identical call returned true while the relay dropped its own ACK. The captured sequence and limitations are in `Command-Workflow-Trace.md`. Full-app and side-effecting-command impact is not established.

In a disposable source-built Copter SITL run, the original library set up signing with a public synthetic key, which the harness also placed into the vehicle state by reflection. A signed parameter request, signed response and signed heartbeats passed independent signature checks. An earlier outgoing status message matched a zero-key signature before setup; matching-tag source explicitly sends a forced-signed connection message and has a zero-key fallback. See `Connection-Telemetry-Trace.md`. Persisted-key discovery, UI, replay handling and physical links remain untested.

Two later SITL runs used an isolated in-memory key registry. With the correct synthetic candidate present, the library adopted it from incoming signed packets and read a parameter. With only a wrong candidate, it did not adopt the key and timed out despite captured signed simulator responses. This tests registry discovery in one local setup; persisted key storage, UI and other channels remain untested.

Two standalone-client SITL runs compared signing behavior on virtual SERIAL0 and SERIAL1. SERIAL0 returned signed parameter responses to unsigned, wrong-key, valid and replayed requests; SERIAL1 responded only to the valid request within each observation window. This is one read-only message on two simulated endpoints, not a general signing or replay assessment. See `Connection-Telemetry-Trace.md`.

On a separately provisioned signed SERIAL1 connection, the original Mission Planner library discovered the matching synthetic registry key and read a parameter. With only a wrong key it logged signature failures and returned from `Open` with the connection closed. These tests used isolated in-memory candidates and a local relay; they do not verify UI key management or physical links.

A separate signed SERIAL1 library run delivered one authentic simulator heartbeat twice, then a signature-corrupted copy. The library's packet event received both identical authentic frames and not the corrupted copy; the log reported a signature failure. This is one heartbeat on a local relay, not a full replay-protection assessment.

In synthetic TCP tests, the distributed transport returned zero bytes after a peer's FIN while `IsOpen` remained true; an explicit close and reopen received data on a second connection. With `autoReconnect` enabled, a separate reset caused a read error and polling `IsOpen` led to a second connection. See `Connection-Telemetry-Trace.md`. Full-application reconnect, MAVLink state recovery and real-link failures remain untested.

An original-library harness also opened a disposable Copter SITL through a local relay, read a parameter, experienced a forced relay reset, explicitly closed and reopened the same interface, and read the parameter again. Packet captures independently show the requests and responses in both sessions. See `sitl-evidence/mavlink-reconnect-probe/summary.json`; automatic recovery, UI recovery and stale-state behavior remain unverified.

Mission Planner flight-mode selection is also partially tested. The original structure-based method sent one `DO_SET_MODE` and two legacy `SET_MODE` packets; delivering either form changed disarmed Copter SITL from STABILIZE to GUIDED, while dropping all three left STABILIZE during the observation window although the method returned. A numeric mode 999 request also returned while SITL reported a failed command ACK and stayed in STABILIZE. Tracker-list fixtures exercised string translation. With test-patched Utilities data paths and local Copter metadata, the original ArduPilot assembly translated mixed-case `gUiDeD` and disarmed SITL reported GUIDED. See `Flight-Mode-Workflow-Trace.md`; metadata download and fallback, other modes, rejection types, UI and flight behavior remain untested.

The guided-position source path and distributed library have also been examined. A disarmed Copter SITL run captured valid global-position packets before and after entering GUIDED and no such packets from three zero-coordinate/altitude calls. A separate airborne retry armed normally, took off, sent a library-generated target approximately 8.9 m north, observed simulated position near the target, and landed with a disarmed heartbeat. An initial attempt failed arming while its position estimate initialized. In a disarmed Plane run, the library sent guided mission items: the MANUAL-mode request received an error that the library logged and swallowed; the GUIDED-mode request received an accepted acknowledgment. See `Guided-Position-Workflow-Trace.md`; UI, automatic GUIDED switching, Plane movement and physical behavior remain untested.

Two additional Plane runs tested lost guided-waypoint acknowledgments. Losing one caused a resend and accepted response; losing all caused 11 item sends and 11 withheld accepted simulator acknowledgments, followed by a logged timeout and normal return to the caller with the library's stored guided target unchanged. The runs were disarmed and did not test movement.

In a separate disarmed Plane run, an error acknowledgment for a MANUAL-mode guided target still updated the library's guided-target cache. A two-item mission's count and item 1 read back unchanged after that rejection and after a later accepted GUIDED-mode target. This is not a full mission-content or UI test.

Two original-library Copter SITL runs uploaded a synthetic WPL waypoint with a NaN latitude. Integer encoding produced an invalid-latitude acknowledgment and preserved the observed prior count and item 1. In the floating-point run, the simulator connection closed and its log reported a floating-point exception; subsequent readback timed out. Its cause and reproducibility remain unverified. See `Mission-File-Trace.md`.

The goal is not complete until scope is explicitly accounted for and the corresponding code, runtime behavior and test evidence have been reviewed. Neither the number of REA records nor successful simulator exchanges prove complete reverse engineering.
