# MAVProxy source and simulator trace

Scope: MAVProxy commit [`8258c223d8da58f2db71a1c2eabb6834f35e8d8c`](https://github.com/ArduPilot/MAVProxy/tree/8258c223d8da58f2db71a1c2eabb6834f35e8d8c), captured 5 November 2026, and selected local Copter SITL behavior. MAVProxy is a separate Python ground station and MAVLink proxy within the ArduPilot organization; it is not the Mission Planner desktop executable. This trace covers selected paths and does not establish complete MAVProxy behavior.

## Source identity and structure

The checkout's `setup.py` declares version `1.8.75`. `research-tools/inventory-mavproxy-source.py` checked the Git index against the worktree at that commit: 87 tracked files matched their Git blob bytes exactly and 389 matched after CRLF normalization. One Gitlink, `MAVProxy/modules/mavproxy_cesium` at `78f7be3dc1511709cdc7427144ab1a2d7c6e33b2`, was not checked or populated. No tracked regular file was missing or mismatched. The manifest is `mission-planner-binary-evidence/mavproxy-source-inventory.json`; source inspection does not establish runtime behavior of untested modules.

The `MAVProxy/mavproxy.py` entry point creates `MPState`, loads the link module and configured modules, establishes master and output links, then runs its main processing loop. `MPState.load_module` imports a module, calls its `init` and registers it if it returns an `MPModule` instance. `process_master` reads master bytes, parses MAVLink and posts messages. The link module's `master_callback` routes messages to outputs and invokes loaded modules' `mavlink_packet` handlers. The reverse `process_mavlink` path can forward parsed slave messages toward a selected master subject to settings such as `mavfwd`; this source observation is not a test of every forwarding or signing case.

The parameter module maintains per-system/component parameter state and handles `PARAM_VALUE`; its periodic fetch path requests a full list or missing indices. The waypoint module derives from `MissionItemProtocolModule`, which handles mission counts and items, orders received sequences, and requests missing items. These are selected source paths, not proof that all parameter, mission or multi-vehicle cases behave correctly.

## Local simulator runs

Three runs launched the pinned source in WSL against the source-built Copter 4.8-dev SITL with `--no-state`, `--no-startup-scripts`, and only `param` and `wp` as default modules. A local UDP output captured forwarded packets. MAVProxy reported vehicle 1:1, 1,431 received parameters, `LOG_DISARMED 0.0`, and a zero-waypoint list. Independent parsing of the UDP capture found respectively 35, 35 and 23 system-1/component-1 heartbeats, all disarmed, and no parser bad-data fragments. These runs exercise a local TCP master, local UDP output, one parameter display and empty mission list; they do not validate Mission Planner UI, actual radios, nonempty mission editing, physical vehicles or all modules.

The first run sent `exit` with the default `requireexit=false`; MAVProxy logged `Unknown command 'exit'`, and the harness terminated the process. In the second, `requireexit=true` was set, but the process did not finish before the harness deadline and was terminated. The third also closed the input pipe after sending `exit`; it exited without harness termination with code 1. The pinned entry point calls `sys.exit(1)` after its module cleanup. The first two attempts and the third run are retained in `sitl-evidence/mavproxy-sitl-smoke/`, `mavproxy-sitl-smoke-2/`, and `mavproxy-sitl-smoke-3/`. `research-tools/summarize-mavproxy-sitl.py` verifies artifact hashes and forwarded telemetry. A direct Windows source launch failed on missing `wx`; WSL was used for these headless runs. An uninstalled-source `--version` attempt failed because package metadata was absent.

## Nonempty mission and final acknowledgment loss

In two fresh, disarmed Copter SITL runs, MAVProxy loaded the same synthetic two-item QGC WPL file through `wp load input.waypoints`. The relay captured the simulator's requests for items 0 and 1 and MAVProxy's two `MISSION_ITEM_INT` uploads. In the normal run the simulator's accepted `MISSION_ACK` reached MAVProxy. In the other run the relay dropped that acknowledgment; MAVProxy still printed `Sent all 2 waypoints`. A separate client connected to SITL SERIAL1 and read count 2 and item 1 back in both runs. Its command, frame, parameters 1–4, integer coordinates, altitude and mission type matched the uploaded waypoint; it was at `-35.3625, 149.166`, altitude 25 m and parameter 1 equal to 2. This verifies one accepted simulator-side upload despite loss of its final acknowledgment, not general upload recovery or safety under other errors.

The source's `process_waypoint_request` prints `Sent all` after sending the requested last item, before observing a final acknowledgment. Both captures contain the simulator's accepted ACK, but the relay did not deliver it in the loss run. Readback of item 0 used `0,0,0` for position and altitude even though the uploaded home had nonzero coordinates and altitude; no equality claim is made for that item. The test sent the file from a relative path. Two earlier attempts used a quoted absolute path containing spaces, elicited `usage: wp load FILENAME` and timed out before sending mission items; their relays then recorded connection resets during cleanup. All four runs and independent packet decodes are retained under `sitl-evidence/command-ack-mavproxy_mission*/`, with checks in `research-tools/summarize-mavproxy-mission.py`.

In a separate disarmed SITL run, MAVProxy first uploaded a valid two-item baseline and an independent client read it back. MAVProxy then uploaded a replacement whose second item used unsupported command 65535. It printed `Sent all 2 waypoints` and subsequently displayed `Got MISSION_ACK: TYPE_MISSION: UNSUPPORTED`; the relay captured accepted and unsupported acknowledgments in that order. A second independent read returned both baseline items with the same sequence, frame, command, parameters 1–4, integer coordinates, altitude and mission type as the first read. This is one rejected replacement, not proof of rollback for other sequences or mission types. `sitl-evidence/command-ack-mavproxy_mission_reject/` holds the fixtures, output and packet captures; `research-tools/summarize-mavproxy-rejected-mission.py` re-decodes them.

## Downstream forwarding settings

Three fresh disarmed SITL runs tested one `PARAM_REQUEST_READ` from a local UDP downstream client, source 211:77, through MAVProxy's output socket. Settings were explicitly set and displayed at startup. With `mavfwd=true` and `mavfwd_disarmed=true`, the master relay captured the unchanged request and the UDP client received `LOG_DISARMED=0`. With both false, the master capture contained no such request and the client received no matching response in its three-second window. With `mavfwd=false` and `mavfwd_disarmed=true`, the request and response were again captured. The third case exercises the source's disarmed forwarding override for this read-only request; it does not test armed behavior or other message types.

The MAVProxy process exited with code 1 in all three runs. The default-setting and fully disabled runs recorded relay-side connection resets; the override run recorded an orderly client close. Those relay errors limit the transport conclusion, but their captures and the downstream probe's observations are retained. `research-tools/summarize-mavproxy-forward.py` checks the request, settings, disarmed heartbeats and response captures in `sitl-evidence/command-ack-mavproxy_forward_*/`. No physical vehicle, actual radio or Mission Planner UI was involved.

Two additional disposable SITL runs tested the same request while the simulated vehicle reported armed. A separate local control client sent simulated force-arm and later force-disarm commands; both received accepted acknowledgments, and that client observed disarmed heartbeats afterward. The UDP capture showed armed heartbeats before and during each three-second request window. With `mavfwd=false` and `mavfwd_disarmed=true`, the external request did not appear on the captured master link and no matching response arrived. With `mavfwd=true` and `mavfwd_disarmed=false`, the unchanged request reached the master and the client received `LOG_DISARMED=0`. This tests one read-only request under forced simulated arm, not flight or other messages.

The first two attempts sent arm commands before estimator initialization; both received failed acknowledgments and timed out without sending the downstream request. The retries waited for the estimator's yaw-alignment notice and an additional three seconds. The blocked-forwarding retry's relay also recorded a connection reset; the enabled-forwarding relay recorded an orderly client close. All four captures are retained in `sitl-evidence/command-ack-mavproxy_forward_armed_*/`; `research-tools/summarize-mavproxy-forward-armed.py` checks the arm/disarm packets, heartbeat states, settings and forwarding observations. No physical vehicle was used.
