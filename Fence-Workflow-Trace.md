# Fence planning and transfer trace

Scope: selected Mission Planner 1.3.83 and pinned ArduPilot source paths, REA method records, and disposable Copter SITL tests. These runs do not establish full UI behavior, real-aircraft enforcement or correctness of every fence geometry.

## Planner and protocol paths

`FlightPlanner.cs` exposes fence as a mission type and defines inclusion/exclusion polygon and circle commands. Its typed fence write path forces fence item frames to `GLOBAL`; it can use MAVFTP `@MISSION/fence.dat` when selected, or the `mav_mission.upload` path. The latter checks the vehicle's reported fence capability and chooses integer items when the vehicle reports `MISSION_INT`. The tests below use MAVLink mission transfer, not MAVFTP or a rendered planner screen.

The source also retains a separate legacy geofence path. `DoGeofencePointsUpload` writes a return point, polygon vertices and a closing point using `setFencePoint`. That method sends `FENCE_POINT`, fetches the point back and accepts a position within five metres, retrying up to three times. These are source observations; the full legacy planner screen was not exercised.

An in-memory test set the selected vehicle's capabilities to zero and its MAVLink 2 flag to false. Both high-level fence upload and download returned the legacy-fence error; both rally upload and download returned the MAVLink 2 requirement error. The fake transport captured zero bytes for these four calls. See `sitl-evidence/fence-capability-synthetic/summary.json`. This tests the guards in that synthetic state, not capability discovery or compatibility with a vehicle.

In `MissionItemProtocol_Fence.cpp`, ArduPilot converts supported fence mission items into polygon, circle or return-point storage items. Polygon vertex count and circle radius are carried in parameter 1. The code stages a new upload and calls `write_fence` at completion. The source does not imply that every rejected transfer is safe to treat as rolled back under every condition. REA method tokens, IL hashes and static call references for selected planner, typed-transfer and legacy methods are in `mission-planner-binary-evidence/fence-method-map.json`.

## Simulator roundtrips

The original Mission Planner communication libraries were connected to disposable, disarmed source-built Copter SITL. In two successful runs using the older typed `setWPTotal`/`setWP` and `getWP` methods, the probe first uploaded a two-item normal mission, then uploaded a fence containing three inclusion-polygon vertices and one exclusion circle. The simulator acknowledged both uploads. Fence readback returned all four commands, vertex counts, radius and integer coordinates; a second normal-mission readback matched the first for the fields compared. A separate run exercised the planner's higher-level `mav_mission.upload` and `download` methods with the same fixtures and obtained matching results. The complete directional captures are decoded in `sitl-evidence/command-ack-fence_roundtrip_retry/summary.json`, `command-ack-fence_roundtrip_stable/summary.json` and `command-ack-fence_highlevel/summary.json`.

Two representation details matter. In these runs the simulator returned normal mission item 0 with latitude and longitude `0,0`, despite nonzero values in the uploaded item; the test compares the two readbacks instead of assuming the uploaded home coordinates survive. Also, the outbound fence items had `autocontinue=1`, while the returned fence items had `autocontinue=0`; that field was not part of the probe's semantic equality check. The first two fence longitudes were encoded as `1491639999` in degrees × 10⁷, one unit below the decimal input's mathematical value. The selected source's integer-item construction casts the scaled floating value to `int`. The effect and relevance of these representation differences outside the captured cases are not established.

The first probe attempt stopped at an incorrect assumption that normal mission item 0 would retain its uploaded coordinates. Its failed assertion and capture remain in `sitl-evidence/command-ack-fence_roundtrip/`; it never reached fence upload. `research-tools/summarize-fence-roundtrip.py` independently decodes all four attempts.

## Copied-storage reboot

A standalone MAVLink client restarted a copy of the first successful simulator's storage. The simulator returned normal mission count two and item zero, then returned a mission error rather than item one. The client did not reach fence readback. This incomplete attempt is retained in `sitl-evidence/fence-mission-reboot/`.

In a second roundtrip the probe waited 12 seconds after readback before closing. A second copied-storage reboot then waited 12 seconds after its initial heartbeat; the standalone client read back both normal mission items and all four fence items. Their sequence, command, parameters 1–4, coordinates, altitude and mission type matched the pre-reboot readback. Raw downlink and storage hashes are decoded in `sitl-evidence/fence-mission-reboot-stable/summary.json` by `research-tools/summarize-fence-reboot.py`. Because both pre-shutdown and startup timing changed, this comparison does not identify the cause of the first failure. It establishes selected fields surviving one simulator restart, not persistence on physical hardware.

## Legacy protocol comparison

The original library's legacy point methods were tested against two disposable Copter simulator binaries. With the prebuilt 4.7.2 binary, the probe set `FENCE_ACTION=0` and `FENCE_TOTAL=5`, then wrote a return point, three polygon vertices and the closing point. All five writes returned true, and ten captured point responses from the implicit verification and explicit readback were within five metres of the supplied coordinates.

Two runs against the source-built 4.8.0-dev binary each set and read back `FENCE_TOTAL=5`, sent point zero and sent four fetch requests, but received no `FENCE_POINT` response before `getFencePoint` timed out. In the second run, the probe also set and read back `FENCE_ACTION=0` and waited two seconds before sending. Both failures are retained. The 4.7.2 capture includes a deprecation notice for `FENCE_FETCH_POINT`. `research-tools/summarize-fence-legacy.py` independently decodes the captures in `sitl-evidence/command-ack-fence_legacy/`, `command-ack-fence_legacy_retry/` and `command-ack-fence_legacy_release/`.

The source comparison accounts for the observed difference. A [4.7-era source revision](https://github.com/ArduPilot/ardupilot/blob/fb773567896014da007bca58358704d4a0d8516f/libraries/GCS_MAVLink/GCS_Fence.cpp) contains a build-guarded legacy point handler; its dispatcher issues the deprecation notice. The supplied 4.8-dev source no longer contains that handler or the fetch-point dispatch. Its build produced the simulator that timed out. The older source defaults the feature guard to zero, but the tested prebuilt binary did respond, so its effective build configuration cannot be inferred from that default. The prebuilt binary reports the first eight characters of the older revision; this does not prove its exact source commit or build options. Five paired source blobs, binary hashes and string anchors are checked by `research-tools/build-legacy-fence-source-comparison.py` and recorded in `sitl-evidence/legacy-fence-source/comparison.json`. These findings do not establish compatibility for other builds or vehicles.

In a separate disarmed 4.7.2 run, the original library wrote and verified the same five legacy points, then read the fence through the typed mission interface. The capture contains four typed items: command 5000 for the return point, followed by three command 5001 inclusion-polygon vertices with vertex count 3. Their locations were within five metres of the corresponding supplied coordinates. The repeated closing point in the legacy representation was not returned as a fourth vertex. The initial client attempt failed because the sandbox blocked its loopback connection and the probe lacked its .NET binding configuration; the successful retry used the same waiting relay with loopback access and the configuration restored. Both logs are retained in `sitl-evidence/command-ack-fence_legacy_interop/`, and `research-tools/summarize-fence-legacy-interop.py` decodes the successful exchange.

The reverse direction was tested in a second disposable 4.7.2 run: the library uploaded the four typed items, then fetched five legacy points. The fifth response repeated the first polygon vertex, closing the triangle. Captured coordinates were within five metres of the supplied points. See `sitl-evidence/command-ack-fence_typed_legacy/` and `research-tools/summarize-fence-typed-legacy.py`. Both directions cover this single return point and inclusion triangle, not every fence shape.

In a third disarmed 4.7.2 run, the original library uploaded a typed return point, inclusion triangle and 25 m exclusion circle. It then requested legacy point zero four times. The simulator sent four `Vehicle contains advanced fences` warnings and no `FENCE_POINT` response; the library timed out. A subsequent typed read returned all five items, matching the uploaded sequence, command, parameters 1–4, coordinates, altitude and mission type. The [candidate older source](https://github.com/ArduPilot/ardupilot/blob/fb773567896014da007bca58358704d4a0d8516f/libraries/AC_Fence/AC_PolyFence_loader.cpp) checks legacy compatibility and sends that warning before returning. The selected binary's exact source and build options remain unproven. Captures and probe are in `sitl-evidence/command-ack-fence_advanced_legacy/`; `research-tools/summarize-fence-advanced-legacy.py` checks the frames. This result does not prove behavior for other advanced shapes, failed uploads or physical devices.

Legacy writes behaved differently from legacy reads in another disposable 4.7.2 run. After the same five-item typed fence was acknowledged, the probe sent one legacy point-zero write with count 6 and new coordinates; the original library's write-and-fetch method returned true. A subsequent typed read reported one item: the new return point. The previously uploaded triangle and exclusion circle were absent from that readback. The candidate older source calls `format()` when a legacy point arrives while the existing fence is incompatible. See `sitl-evidence/command-ack-fence_advanced_write/` and `research-tools/summarize-fence-advanced-write.py`. This is one selected simulator build and one write, not proof of behavior for all versions or hardware.

## MAVFTP fence transfer

The planner's optional MAVFTP path packs mission items using `missionpck.pack`, uploads `@MISSION/fence.dat`, and downloads and unpacks that file on read. Source selects the path via `UseMissionMAVFTP`; on read or write exceptions it has additional handling, so a standalone library probe does not establish screen behavior. REA's captured original ArduPilot assembly metadata contains `missionpck.unpack` token `0x06000674`, `pack` token `0x06000675`, `MAVFtp.GetFile` token `0x06000745`, and two `UploadFile` overloads `0x06000746` and `0x06000747` in `mission-planner-binary-evidence/rea-ardupilot-all-members.json`.

In a disposable source-built 4.8-dev Copter run, a harness used those original library methods to upload a four-item inclusion triangle plus exclusion circle through MAVFTP. It pumped the interface's packet reader while FTP operations ran. The captured upload carried the 162-byte packed file in three writes; normal mission-protocol readback and a subsequent MAVFTP download returned four items. The download and mission-protocol items matched the uploaded command, four parameters, integer coordinates, altitude and frame. The downloaded file had sequence numbers 0–3 and mission type 1, while the harness's original packed items carried zero in those fields. Other item fields are not claimed equal. `research-tools/summarize-fence-mavftp.py` checks the packet data, file contents and both runs in `sitl-evidence/command-ack-fence_mavftp_pumped/` and `command-ack-fence_mavftp/`.

The first harness attempt omitted the packet reader. Its FTP requests and replies were captured, but the library did not process those replies during the FTP calls. `UploadFile` returned normally even though the normal mission-protocol count was zero; a later null download caused the probe to fail. This is an observation about that incomplete harness, not evidence that normal Mission Planner UI uploads silently fail. The source `UploadFile` method calls lower-level operations without checking their boolean returns; the packet-pumped run provides a contrasting working setup. No hardware, UI checkbox interaction or corrupted FTP data was tested here.

A separate packet-pumped 4.8-dev run tested sustained loss. It first uploaded a four-item baseline fence through the regular mission protocol, then attempted a different fence through MAVFTP. A local relay delivered the create request and response but dropped all 30 subsequent write requests. The original `UploadFile` call returned without an exception. A normal mission read afterward returned all four baseline items, matching sequence, command, parameters 1–4, integer coordinates, altitude and mission type; the attempted replacement had a 25 m circle instead of the baseline's 15 m circle. Source `UploadFile` ignores the lower-level write method's Boolean result, which is consistent with this observation. Captured frames and independent decoding are in `sitl-evidence/command-ack-fence_mavftp_drop_writes/` and `research-tools/summarize-fence-mavftp-drop.py`. This single synthetic-loss run does not establish the planner UI's feedback or behavior under partial writes, loss of acknowledgments, or real links.

Two further packet-pumped runs began with the same baseline and replacement. In the first, the relay accidentally dropped only the middle 80-byte write at offset 80; it delivered writes at offsets 0 and 160 and the last write's acknowledgment. The call returned normally, and the subsequent typed read matched the baseline rather than the replacement in the compared fields. In the second, all writes reached SITL but the relay dropped all 30 acknowledgments for the final write at offset 160. The client sent that final write 30 times and returned normally after retries; readback matched the replacement in the compared fields. A returned `UploadFile` call therefore did not distinguish these two outcomes in these tests. The source's batched write callback marks completion on the last chunk's acknowledgment without first checking that every earlier chunk was acknowledged; this is consistent with the middle-chunk observation, though the test does not prove every internal step.

The middle-chunk relay was intended to drop both later writes, but its length check missed the final short MAVLink 2 frame. Two initial attempts to drop the final acknowledgment also dropped nothing: first because of the same trailing-zero truncation, then because the relay used the wrong FTP header index. Their full captures are retained as `command-ack-fence_mavftp_partial/`, `command-ack-fence_mavftp_last_ack/` and `command-ack-fence_mavftp_last_ack_fixed/`. The corrected acknowledgment-loss run is `command-ack-fence_mavftp_last_ack_retry/`. `research-tools/summarize-fence-mavftp-loss.py` decodes all four. These are simulator and library observations; planner UI behavior and real radio links remain untested.
