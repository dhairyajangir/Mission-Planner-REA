# Connection and telemetry trace

These observations refer to Mission Planner 1.3.83 source and the selected 4.7.2 SITL tests. They do not establish behavior for every transport, firmware release or interface.

## Source path

1. `mission-planner-1.3.83-source/MainV2.cs:1432` chooses a transport for a connection. The branches at `:1458` onward include TCP, UDP, WebSocket and UDP-client variants. `doDisconnect` is at `:1373`.
2. `ExtLibs/ArduPilot/Mavlink/MAVLinkInterface.cs:654` defines the `Open` path. The default connection timeout is read from settings with a 30-second fallback (`:325`). The connection loop gathers heartbeat or high-latency messages, excludes ground-station heartbeats and component ID zero, and groups observations by system/component (`:811` onward). It selects component 1 after two observations, or another component after four, as shown in that source snapshot. Missing or insufficient heartbeats follow separate error paths.
3. `MainV2.cs:3035` reads packets from open ports while the port is available to the reader. `:3048` updates each vehicle's `CurrentState`. This source also uses a `giveComport` coordination flag; its complete concurrency behavior and all reconnection cases still need review.
4. `ExtLibs/ArduPilot/CurrentState.cs:2901`, `:3202`, `:3218`, `:3246` and `:3798` handle `SYS_STATUS`, `ATTITUDE`, `GLOBAL_POSITION_INT`, `GPS_RAW_INT` and `VFR_HUD` respectively. UI bindings in `GCSViews/FlightData.cs` consume state values. Some values include unit conversions, firmware-dependent choices or derived calculations; each displayed field needs its own trace before claiming parity.

## Observed behavior

The isolated pymavlink smoke test initially received a heartbeat but did not receive three expected telemetry streams within its test window (`sitl-evidence/smoke-run/results.json`). A subsequent run explicitly requested streams and received heartbeat, attitude, global position and system status (`smoke-run-2/results.json`). This establishes those particular exchanges with the tested binary; it does not prove what would occur with different stream settings.

The separate Mission Planner library harness established a TCP connection to SITL and reported system 1, component 1 (`sitl-evidence/missionplanner-probe/windows-probe-binding.log`). The harness invoked the library without the Mission Planner UI. Its initial assembly-binding failure and the corrected run are both retained.

An application-level probe used a test-only Mission Planner copy with two data-directory methods redirected and plugins disabled. Its own startup script connected to the locally built 4.8.0-dev SITL through a file-backed transport and a relay fixed to localhost; it reported `open=True`, system/component 1/1 and mission count 0 (`sitl-evidence/integrated-spool-probe/application-result.txt`). The corresponding relay transferred bytes in both directions without a reported relay error. The state probe still returned latitude and longitude 0.0, so it did not verify telemetry presentation. This is a modified application environment with a test transport, not a test of the original TCP UI workflow.

A fresh run explicitly requested all telemetry streams at 4 Hz. Its application state reported latitude `-35.363261000000001` and longitude `149.16522990000001`, matching the simulated home within the test tolerance (`sitl-evidence/integrated-spool-telemetry/application-result.txt`). `relay-result.json` records nonzero traffic in both directions and no relay errors. This verifies the app's state update in the test environment; the rendered map and HUD were not observed.

## In-memory MAVLink signing test

The distributed Mission Planner communication library was given synthetic MAVLink 2 heartbeat frames through a test-only in-memory `ICommsSerial`; no operating-system serial port, network, GUI or vehicle was involved. A public test key containing bytes `00` through `1f` was installed directly in the test vehicle state by reflection. The fixture generator independently computes the MAVLink checksum and the six-byte signature from SHA-256 over the test key, packet and seven-byte signature header. Fixture hashes, generator, harness and output are preserved under `sitl-evidence/live-signing-probe/` and `research-tools/`.

With this injected key and `signingignore=false`, the library returned the correctly signed packet and rejected a packet with its last signature byte changed. Setting `signingignore=true` caused that altered packet to be returned. In separate fresh harness instances, the library returned the same signed packet twice and also returned an unsigned packet when the state had `signing=true`. In a further test, a valid signed packet set the state to `signing=true`, and a following unsigned heartbeat was returned with that state still true. The duplicated packet used an old fixed signature timestamp. These are observations of the specific parser invocation and manually constructed state; they do not establish behavior of a normally connected vehicle, fleet-wide replay protection, or other transports and message types.

The source checks signatures on signed packets when `signingignore` and `logreadmode` are both false (`MAVLinkInterface.cs:5057–5085`); `CheckSignature` hashes the key and packet and compares six signature bytes (`:5498`). In this source path the signature timestamp is converted and a time delta calculated, but the displayed code does not use that delta for a rejection. Source-to-distributed-binary equivalence was not proven; the source description is consistent with the synthetic observations and is not a claim about ArduPilot firmware acceptance.

## In-memory system and component separation

The distributed communication library's `readPacket()` was exercised with synthetic MAVLink 1 frames supplied by an in-memory transport. With vehicle heartbeats from `1:1` and `2:1`, a GCS heartbeat from `255:190`, and a camera heartbeat from `1:100`, the parser exposed four entries and retained `1:1` as the selected entry. When the GCS heartbeat came first in a fresh parser instance, it became selected and remained selected after the two vehicle heartbeats. A separate corrupted-checksum heartbeat was rejected and did not create the test system-3 entry. The source raw-packet heartbeat branch promotes detected system/component pairs and defaults to the first visible entry (`MAVLinkInterface.cs:5276–5304`); its connection-opening handshake has different filtering and was not invoked in this test.

Another fixture gave the same synthetic parameter name three values: 12.5 from `1:1`, 87.5 from `2:1`, and 42 from `1:100`. After parsing, the three respective parameter caches returned those values. A later corrupted packet claiming a value of 99 for `2:1` returned an invalid message and left that cache at 87.5. A separate pymavlink decode verified the fixture frames and recorded checksum failures. Evidence and hashes are in `sitl-evidence/multivehicle-parser-probe/`.

The raw parser tests did not invoke `Open()`. A second test invoked the distributed library's `Open(false, false, false)` using a timed in-memory transport that repeatedly supplied the GCS-first, vehicle-1 and vehicle-2 heartbeats. Although the GCS arrived first, the handshake logged `HB Selection 1-1 seen 2` and returned with `1:1` selected; all three entries, including the GCS, appeared in the visible list. The fake transport did not answer the version request. The library logged three version retries and still reported the test transport open. The test harness's writes were discarded; it did not simulate complete vehicle responses. Output and the independently decoded input fixture are in `sitl-evidence/multivehicle-parser-probe/handshake.log` and `summary.json`.

These are synthetic in-memory tests, not an active network, vehicle or UI. They do not establish normal transport behavior, complete version negotiation, real component discovery, stale-vehicle handling, concurrent packet behavior, or screen behavior.

## Still untested

Mission Planner's on-screen indicators and controls, serial/UDP/WebSocket connections, reconnect behavior, stale telemetry, packet loss and connection failure handling need further direct tests. Later sections record bounded local multi-vehicle and signed SITL connection experiments. A successful localhost TCP exchange or an in-memory parser test does not prove physical-link or full-application behavior.
# Two simulated vehicles through a local relay

The distributed Mission Planner library connected over localhost to a frame-aware relay serving two source-built Copter SITL processes. The simulators reported system/component IDs 1:1 and 2:1. The library discovered both and initially selected 1:1. Explicit requests for `LOG_DISARMED` returned 0 and 1 respectively; requests after changing the library's selected system returned the same values. Both cached values matched. A write addressed to 2:1 changed that simulator's value back to 0, confirmed by a subsequent read. The independently decoded capture contains heartbeats from both system IDs, requests addressed to both, and the write and responses from system 2.

Evidence: `sitl-evidence/dual-sitl-library-attempt3/summary.json`, `probe.log`, `relay-result.json`, and captured binary streams; `research-tools/summarize-dual-sitl.py` re-decodes the captures. The relay concatenated complete MAVLink frames from two simulator streams and duplicated application uplink to both; it dropped 2 and 12 parser-reported bad-data fragments respectively, so this is a relay-mediated test, not proof of an unmodified network topology. It exercised the library without the full application UI or real aircraft. The first two setup attempts failed because this source uses `MAV_SYSID`, while the attempted older `SYSID_THISMAV` default did not set the second simulator's ID. Those attempts remain in `dual-sitl-library` and `dual-sitl-library-attempt2`.

In the matching-version source checkout, `ExtLibs/ArduPilot/Mavlink/MAVList.cs` uses the combined key `sysid * 256 + compid`. An indexer lookup for an unknown pair creates a hidden state; `Create` can move that state into the visible list. The indexer checks hidden states first, while `Contains` can include or exclude them. These source details explain why the probe explicitly checked visible entries with `includehidden=false`; they do not establish how every application screen presents multiple vehicles.

One UI selection path is `GCSViews/FlightData.cs:6028`: on map mouse-up, a marker tagged with a vehicle state can select its parent port, system ID and component ID when `ClickSwapMAV` is enabled and the recorded start and end positions match. The library's two ID property setters each raise `MavChanged` when their value changes (`MAVLinkInterface.cs:291` and `:305`). In a separate property-only harness, changing 1:100 to 2:1 in that order emitted events for 2:100 and then 2:1 (`sitl-evidence/multivehicle-parser-probe/selection-events.log`). The source's main-window subscriber (`MainV2.cs:1099`) reads the current `MAV` and assigns its current-state object to HUD, warning and checklist sources. In a second synthetic run, a subscriber that read `MAV` during each event left 2:100 present as hidden and absent from the visible list (`selection-events-state.log`). This observes an intermediate event state; it does not establish a user-visible error. Neither test exercised the map handler or its actual subscribers.

The matching source's `MAVList.Clear()` clears `masterlist` but not `hiddenlist`; the `logplaybackfile` setter calls `Clear()` (`MAVLinkInterface.cs:400`). In-memory runs confirmed that the hidden 2:100 entry remained detectable after `Clear()` and after setting `logplaybackfile` to null (`selection-events-clear.log` and `selection-events-playback.log`). No log file was loaded and the test does not establish whether the retained state causes a fault.

# TCP transport close and explicit reconnect

In one localhost test against the distributed `MissionPlanner.Comms.dll`, a scripted peer sent `FIRST`, received marker `X`, then shut down its sending half of the TCP connection. `TcpSerial.IsOpen` was still `True` before the next read; that read returned zero bytes, and `IsOpen` was still `True` immediately afterward. Calling `Close()` made `IsOpen` false and cleared the `Host` property. After the harness restored `Host` and explicitly called `Open()`, the same transport object received `SECOND` from the peer's second accepted connection. The separate peer event log records the first FIN and both client closes.

Evidence: `sitl-evidence/tcp-reconnect-probe/probe.log` and `peer-result.json`; harness and peer are `research-tools/TcpReconnectProbe.cs` and `tcp-reconnect-peer.py`. This was a synthetic TCP peer with `autoReconnect` left at its default; it did not run `MAVLinkInterface.Open`, the Mission Planner UI, a real telemetry link, or automatic reconnect. The result is limited to this graceful half-close sequence and this distributed library/runtime. The matching-tag source implements `IsOpen` through `TcpClient.Client.Connected` and resets `Host` in `Close()` (`ExtLibs/Comms/CommsTCPSerial.cs`).

In a separate local test, `autoReconnect` was enabled and the peer reset the first TCP connection after receiving marker `X`. `IsOpen` initially reported true, the following read raised `Socket Closed`, and repeated `IsOpen` checks led to a second accepted connection that delivered `SECOND`. The peer log confirms both connections (`sitl-evidence/tcp-autoreconnect-probe/`). This does not establish whether the full application enables this option, recovers MAVLink state, or behaves similarly for silent outages, partial packets or other network failures.

In matching-tag source, the main TCP connection branch constructs `new TcpSerial()` (`MainV2.cs:1458`), whose `autoReconnect` field defaults to false. Other source paths explicitly enable it, including `Controls/MovingBase.cs:77` and `Controls/SerialOutputNMEA.cs:71`. These are construction-site observations, not a runtime proof of the main application's eventual setting or recovery behavior.

The matching source's `TcpSerial.Write(byte[], int offset, int length)` calls the socket send overload with the buffer and length but does not use `offset` (`CommsTCPSerial.cs:237`). A localhost harness against the distributed library called `Write` with ASCII `ABCDEFG`, offset 2 and length 3. Its peer received `ABC`, not the requested slice `CDE` (`sitl-evidence/tcp-write-offset-probe/`). This is one direct API behavior observation; no affected Mission Planner UI or MAVLink workflow has been established.

The same source method has an empty catch around `Socket.Send` after `VerifyConnected()`. In a separate local test, the peer reset the connection after an initial marker; the harness then observed `IsOpen=True`, called `Write` without receiving an exception, and observed `IsOpen=False` afterward (`sitl-evidence/tcp-reset-write-probe/`). The peer had already closed. The fixture does not establish how a real command or the full application reports such a failure.

In a separate test with the original `MAVLinkInterface` and a disposable source-built Copter SITL, a local byte relay reset the first TCP session after a successful `LOG_DISARMED` read. The harness observed `IsOpen=True` immediately after the reset, explicitly called `Close()`, restored the TCP host and called `Open()` again on the same interface. The second session selected system/component 1:1 and read `LOG_DISARMED=0` again. Independently decoded captures contain a heartbeat, targeted parameter request and matching response in each session (`sitl-evidence/mavlink-reconnect-probe/summary.json`). The decoder counted 53 bad-data fragments in the first downlink and none in the second; the relay forwarded raw bytes without filtering. This demonstrates explicit reopen in this controlled setup, not automatic recovery, full UI behavior or stale-state correctness.

The matching-tag `MainV2` serial-reader loop (`MainV2.cs:2990` onward) tests `IsOpen` and only enters its packet-reading loop when `BytesToRead` exceeds its threshold. It removes closed non-primary ports, while an exception escaping the enclosing loop causes `comPort.Close()` to be called. Those source branches have not been exercised by the transport fixtures above. In particular, the FIN fixture's stale `IsOpen` result does not by itself prove how the application displays or handles that condition.

# Synthetic signing against Copter SITL

The original Mission Planner library opened a local source-built 4.8-dev Copter simulator, read `LOG_DISARMED=0`, and called `setupSigning` with the public test key consisting of bytes 0 through 31. The harness explicitly set the selected vehicle state's private signing key by reflection after the setup call. A subsequent signed parameter request received a signed `PARAM_VALUE` of 0; independent SHA-256 checks matched the test key for that request, the response, and two signed simulator heartbeats. Captured heartbeats reported the vehicle disarmed. This tests an explicitly injected synthetic key, not the application's normal key lookup or UI setup workflow.

One earlier outgoing `STATUSTEXT` frame, `Mission Planner 0.0`, had a signature matching an all-zero 32-byte key, not the test key. It appeared before the first parameter request and before the two setup messages in the captured uplink. The matching-tag source's connection routine explicitly sends a forced-signed status message alongside two unsigned variants, and its packet generator falls back to a zero key when the selected state has no 32-byte key. This source path is consistent with the captured frame; source-to-binary identity and whether SITL acted on the frame are not established. The source `setupSigning` sends two setup packets and enables the signing state, relying on separate key adaptation; this probe did not test that adaptation because it supplied the state key directly. REA metadata records `setupSigning` as method token `0x0600043e` and `CheckSignature` as `0x06000498` in the distributed ArduPilot assembly.

The relay capture and synthetic key are in `sitl-evidence/command-ack-signing_sitl/`; `research-tools/summarize-signing-sitl.py` decodes frames and checks signatures. A wrapper process failed while printing the log because of console encoding after it had already saved the probe output and exit code; the probe itself exited zero. The result does not establish replay protection, bad-signature rejection by the simulator, unsigned-message policy, persistence, physical-device behavior or full-app operation.

## Synthetic key discovery

Two further source-built Copter SITL runs used the original library's in-process `MAVAuthKeys` registry, with its user-data path redirected to an empty workspace directory before registry initialization. Both added an intentionally wrong synthetic seed; one also added the matching seed. The library sent two setup messages using the matching seed's SHA-256 key. In the matching run, the selected vehicle's key was initially null, then became equal to the registry key after the harness read incoming packets. A signed parameter request and signed response both matched that key, and the library returned `LOG_DISARMED=0`. The harness read the private field to observe adoption; it did not write it.

In the wrong-key-only run, the selected state key remained null and the library logged signature failures and timed out waiting for the parameter. Its signed requests matched the library's all-zero fallback key; the captured simulator responses and heartbeats matched the actual test key. The capture contains signed responses during the attempt, even though the library did not return a parameter value. Source signing policy permits unsigned traffic on channel 0 under a secure-channel assumption, but these observations alone do not establish why the simulator responded to the requests or what another channel would accept. `research-tools/summarize-signing-discovery.py` independently checks both runs in `sitl-evidence/command-ack-signing_discovery_match/` and `command-ack-signing_discovery_missing/`. This exercises the in-memory key registry and local TCP/SITL path; persistent key storage, UI controls, hardware and replay handling remain untested.

## Standalone signing policy comparison

Two fresh source-built Copter SITL runs used a standalone MAVLink client and a synthetic key. In each run, the client configured signing through TCP port 7560, logged by SITL as `SERIAL0`, then sent identical types of `LOG_DISARMED` request through that endpoint and port 7562, logged as `SERIAL1`. Each endpoint was observed for 1.5 seconds after each request. Both runs returned one signed response for each of the unsigned, wrong-key, valid-key and exact-replay requests on SERIAL0. On SERIAL1, both returned one signed response to the valid-key request and no matching response during the observation window for the unsigned, wrong-key or replay request. This tests one read-only message, one signing configuration and these local endpoints; lack of a response is not a complete proof of message rejection or of other commands' behavior.

The matching source's `GCS_Signing.cpp` accepts unsigned or incorrectly signed packets on `MAVLINK_COMM_0`, described there as an assumed secure channel, and otherwise permits a short radio-message list. That source branch is consistent with the endpoint distinction; the test did not instrument internal channel assignments. The source file matches Git blob `8faffa7894bec6f3c2cdffd2172ee18986193b76` in the pinned archive candidate tree. `research-tools/summarize-signing-channel-sitl.py` verifies signatures and re-decodes byte-bounded request/response windows in `sitl-evidence/signing-channel-sitl-2/`; the first run and its captures are in `sitl-evidence/signing-channel-sitl/`. The Mission Planner UI, hardware, other messages and radio links were not tested by this standalone client.

## Mission Planner library on a signed SERIAL1 connection

In two additional fresh simulations, a standalone bootstrap client set a synthetic signing key through SERIAL0 and observed correctly signed disarmed heartbeats on both serial endpoints. A local relay then connected the original Mission Planner library to SERIAL1. The library's candidate-key registry used an isolated workspace user-data directory. In the matching-key run, `Open` returned with the connection open and vehicle 1:1 selected; the library adopted the key and read `LOG_DISARMED=0`. Captured request and response signatures matched the synthetic key.

In the wrong-key-only run, the library logged signature failures and an internal `InvalidOperationException: Sequence contains no elements`. `Open` returned to the harness with `IsOpen=False` and selected IDs 0:0; no parameter request was sent. The harness caught no exception from `Open` itself. This is an observed library failure path, not a claim about what the full application displays. `research-tools/summarize-signing-serial1.py` checks bootstrap and relayed captures in `sitl-evidence/signing-serial1-match/` and `signing-serial1-missing/`. The tests use a local relay, synthetic keys and a disarmed simulator; persistent key management, physical interfaces and normal UI connection remain untested.

In a separate matching-key SERIAL1 run, the relay captured an authentic signed simulator heartbeat during bootstrap and delivered that exact frame twice to the library, followed by a copy with one signature byte altered. A handler subscribed to the original library's `OnPacketReceived` event recorded the authentic frame's SHA-256 twice and did not record the altered frame; the library logged one signature failure. The connection then opened and a signed parameter read returned 0. Captured bytes and signature checks are in `sitl-evidence/signing-serial1-replay-match/`, verified by `research-tools/summarize-signing-replay-sitl.py`. This confirms duplicate acceptance and altered-signature handling for one heartbeat through this local library connection, not full application behavior, other messages or every replay scenario.
