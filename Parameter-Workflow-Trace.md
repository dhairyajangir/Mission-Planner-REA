# Parameter workflow trace

This trace covers selected parameter operations in the Mission Planner 1.3.83 source and two ArduCopter SITL versions. The supplied 4.8.0-dev archive has separately verified commit `72b238201f5ea3b556e3809b2ec704fcf701474a`. The prebuilt 4.7.2 simulator's version metadata identifies commit `fb773567896014da007bca58358704d4a0d8516f`; observations from that binary should not be attributed to the 4.8.0-dev archive without a version-matched test.

## Ground-station code

- `mission-planner-1.3.83-source/ExtLibs/ArduPilot/Mavlink/MAVLinkInterface.cs:2293`: `GetParamAsync` builds a `PARAM_REQUEST_READ` for a name or index, waits for a matching `PARAM_VALUE`, retries and times out if it receives no matching response. A received value is placed into the vehicle's local parameter and type lists.
- `MAVLinkInterface.cs:1635`: `setParamAsync` first checks the local vehicle parameter list; an absent name returns false without proving whether the vehicle itself knows that name. For a known parameter it sends `PARAM_SET` and waits for the matching `PARAM_VALUE` response.
- `MAVLinkInterface.cs:1778`, `:1810`, and `:1945`: parameter-list methods include MAVLink FTP and regular parameter-protocol paths. The FTP wrapper catches errors and falls through to the regular path when it does not return an unpacked list (`:1927`).
- `GCSViews/ConfigurationView/ConfigRawParams.cs:519` queues edited values. The Write Params handler at `:257` displays a confirmation and calls `setParam` for queued entries (`:298`, `:323`); it then displays a success or partial-failure message (`:367`).

## Autopilot source starting points

The 4.8.0-dev archive dispatches a parameter-read message at `libraries/GCS_MAVLink/GCS_Common.cpp:4308`; handlers for reading and setting parameters are in `libraries/GCS_MAVLink/GCS_Param.cpp:225` and `:265`. These are source navigation references, not a substitute for checking the tested 4.7.2 binary's exact behavior.

## Observed tests

The unmodified Mission Planner 1.3.83 communication assemblies were called by `research-tools/MissionPlannerMavlinkProbe.cs` against a local SITL instance. No physical aircraft was connected.

1. `GetParam("WPNAV_SPEED")` retried and timed out (`sitl-evidence/parameter-probe/library-parameter-test.log`). A separate pymavlink discovery did not receive that name in its five-second query window, but did receive `LOG_DISARMED`, `FRAME_CLASS`, `SIM_SPEEDUP` and `RTL_ALT_M` (`sitl-evidence/parameter-discovery/results.json`). The reason for the missing response is not established.
2. A second harness run read `LOG_DISARMED=0`, set it to 1, read back 1, then restored and read back 0 (`sitl-evidence/parameter-probe/library-parameter-test-2.log`). The simulator's original value was restored in a `finally` block.
3. In that run, `setParam` returned false for a name absent from the harness's local parameter list. The code checks that list before sending; this result is not evidence of how the autopilot responds to an unknown `PARAM_SET`.
4. Against the locally built 4.8.0-dev Copter, a harness using the original library called the non-GUI `getParamList(sysid, compid)` with a packet reader. The library reported 1,431 received and 1,431 reported, and logged 1,431 unique indexes (`sitl-evidence/param-list-probe/library-list.log`). This exercised the regular parameter protocol in one uninterrupted run; it did not exercise MAVLink FTP or compare every value independently.
5. A fresh source-built 4.8.0-dev simulator and a second harness run called `getParamListMavftp`. The transcript shows an FTP open of `@PARAM/param.pck?withdefaults=1`, parsing by `parampck`, and 1,431 received and reported (`sitl-evidence/param-ftp-probe/library-list.log`). The FTP implementation logged an end-of-file response as an error before parsing continued. Values were not independently compared against the regular-protocol run; failure and fallback behavior were not injected.
6. A modified, plugin-disabled Mission Planner test copy connected to disposable source-built Copter SITL via the local file-spool relay. After the application loaded 1,431 parameters, the Full Parameter List search returned `LOG_DISARMED`; its value was edited from 0 to 1. The confirmation listed that single change, and the subsequent Saved dialog reported one parameter saved. The application log recorded the queued change and `setParam` response of 1. A separate MAVLink client on the simulator's second local TCP endpoint independently read 1. The test script then restored the value to 0, and the separate client independently read 0 (`sitl-evidence/integrated-ui-params-write/`). The parameter grid still displayed 1 after the scripted restoration and disconnect; no UI refresh was performed. UI screenshots were inspected but not retained. This is one parameter and one patched application run, not evidence that every setting or screen synchronizes correctly.
7. A standalone Mission Planner library harness connected through a local proxy to fresh source-built Copter SITL. The proxy dropped every FTP reply while forwarding the other traffic. The captured client stream included ten FTP requests and one `PARAM_REQUEST_LIST`; ten dropped downlink frames independently decoded as valid MAVLink FTP packets. Byte comparison showed the uplink was unchanged and the downlink differed only by those ten packets. The 164 non-frame bytes were simulator startup text and were forwarded unchanged. The harness logged an FTP attempt and then 1,431 received, reported and unique parameter indexes (`sitl-evidence/archive-param-ftp-drop-2/`). A first run reached the same list count but its proxy's strict zero-non-frame check failed; that result is retained in `archive-param-ftp-drop/`. This exercises a complete loss of FTP replies during one list operation, not arbitrary packet loss or all fallback conditions.
8. In another disposable SITL run, a proxy discarded the first `PARAM_VALUE` frame for each list index 20–29 after the regular `PARAM_REQUEST_LIST`. Independent decoding confirmed ten valid dropped values, ten individual `PARAM_REQUEST_READ` messages for those same indexes, and later forwarded values for all ten. The harness reported 1,431 received, reported and unique indexes. Captured byte streams confirm that the uplink was unchanged and the downlink differed only by the ten selected frames (`sitl-evidence/archive-param-index-loss/`). This is one contiguous, one-time loss pattern; disconnected links remain untested.
9. A separate run discarded the first values for indexes 0–499. The library logged 931 of 1,431 received, below its calculated 75% threshold of 1,071, and requested the whole list again. The captured uplink contained two `PARAM_REQUEST_LIST` messages; independent decoding of the forwarded downlink found all 500 previously dropped indexes. The harness reported 1,431 received, reported and unique indexes (`sitl-evidence/archive-param-bulk-loss/`). Captured streams matched after removing exactly the 500 valid selected frames. This checks one single-burst loss pattern, not a permanently degraded connection.
10. A third loss pattern discarded three consecutive `PARAM_VALUE` frames for index 20, including the first copy from the list. The library sent three individual reads for index 20; the last response reached it and the harness reported all 1,431 indexes (`sitl-evidence/archive-param-repeat-loss/`). Independent decoding and stream comparison verified the three dropped packets and the later forwarded value. This bounded test does not establish an eventual timeout under indefinite loss.

The tests do not establish general settings-screen behavior, synchronization after packet loss, disconnection during a write, reboot persistence, or calibration.

## Parameter file behavior

`ExtLibs/Utilities/ParamFile.cs:17` parses parameter files by splitting on spaces, commas and tabs and parsing the second token using invariant culture. It skips certain parameter names after parsing their values, and later duplicate names overwrite earlier entries. The raw-parameter screen calls this loader, stages matching rows, and can add missing names to its offline parameter list (`ConfigRawParams.cs:128–216`); writing to a connected vehicle is a separate action. This is a source trace, not a test of that screen.

A harness using the distributed `MissionPlanner.Utilities.dll` tested synthetic files. The last of two duplicate values was returned; `SYS_NUM_RESETS` and `FORMAT_VERSION` were omitted. The input `DECIMAL_COMMA,1,25` was read as value 1 because commas are delimiters. A `NaN` token was accepted as a non-finite double. An indented comment, an ordinary invalid number, and an invalid value for the otherwise-excluded `FORMAT_VERSION` each raised `FormatException`; exclusion occurs after numeric parsing in the source. These are specific fixtures, not a complete format specification.

Under a test thread culture of `de-DE`, the library saved numeric values using dot decimals. The saved file included `FORMAT_VERSION`, while loading it omitted that key; the two remaining test values round-tripped. This one culture and set of values does not establish all locale behavior. Files, logs, harness and hashes are retained in `sitl-evidence/param-file-probe/`.

## Non-finite writes to source-built SITL

The verified archive's `GCS_Param.cpp:284` rejects NaN and infinity in `PARAM_SET` before writing the value. In a separate standalone MAVLink 2 test, a fresh source-built Copter simulator began with `LOG_DISARMED=0`. Sending NaN, positive infinity and negative infinity each produced `PARAM_ERROR` code 2 for that parameter, and a subsequent parameter read returned 0. A finite control write to 1 was read back as 1; the test restored 0 and read back 0 (`sitl-evidence/archive-copter-nonfinite-param/results.json`).

This standalone test did not feed the file parser into the planner UI or Mission Planner's `setParam` method. It demonstrates the specified behavior of one parameter on this simulator build, not all firmware versions, all parameter protocols, or physical aircraft.

## Mission Planner library against the same firmware snapshot

A separate Windows harness used the distributed utility and communication libraries with a fresh source-built localhost simulator. It loaded a synthetic `LOG_DISARMED,NaN` file, confirmed that the parsed value was NaN, connected, and read an initial value of 0. The library logged `Unknown Packet 345` four times while attempting the write, logged three retries, and raised `TimeoutException` for `setParam`; a subsequent library read returned 0. A finite write to 1 and restore to 0 both returned successfully and were read back through the same library. The harness reported that the distributed `MAVLINK_MSG_ID` enum has no member named `PARAM_ERROR`. The fixture, binary hashes, host cleanup result and full output are in `sitl-evidence/missionplanner-nonfinite-probe/`.

The source library's `setParamAsync` subscribes to `PARAM_VALUE` and retries while waiting for it (`MAVLinkInterface.cs:1679–1768`). The separately decoded simulator test above observed `PARAM_ERROR`, whose MAVLink message ID is 345, for each non-finite write. That provides a consistent explanation for the library's unknown-packet and timeout logs, but the library test did not capture and independently decode the wire packets, so their payloads were not verified there. This was a library harness, not the UI, and the same-library readback is not an independent client measurement.

A second, fresh library/SITL run used a passive localhost TCP relay that saved both forwarded byte streams. Offline decoding with the separately bundled pymavlink dialect found four `PARAM_SET` packets carrying NaN for `LOG_DISARMED` and four `PARAM_ERROR` packets for the same name with code 2. The directional captures do not timestamp individual frames, so they do not independently pair each request with a particular response. The decoder also reported 53 downlink `Bad prefix` records; their origins were not established, and their feed offsets and samples are retained in `decoded.json`. No bad-data records were reported in the uplink. The library again logged unknown packet 345 and timed out; the capture also contains a finite write to 1, a restore to 0, and returned values for both. The proxy reported a normal client close and no relay errors. Raw streams, hashes, decoder output and harness log are in `sitl-evidence/missionplanner-nonfinite-capture/`. This confirms those decoded messages in the second run; it does not test the UI, other firmware releases or physical hardware.
