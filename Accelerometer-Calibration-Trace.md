# Accelerometer calibration trace

Scope: Mission Planner 1.3.83 source and original distributed library, paired with the source-built Copter simulator from the supplied ArduPilot archive. This is a partial workflow trace; it includes one simulator-reported complete calibration and no physical sensor test.

## Source path

`mission-planner-1.3.83-source/GCSViews/ConfigurationView/ConfigAccelerometerCalibration.cs` starts full accelerometer calibration with `PREFLIGHT_CALIBRATION`, parameter 5 set to 1. If `doCommand` returns true, the control sets its in-calibration state and subscribes to `STATUSTEXT` and `COMMAND_LONG`. It displays a requested position from `ACCELCAL_VEHICLE_POS`; a subsequent click sends that position back in a `COMMAND_LONG`. Status text containing “calibration successful” or “calibration failed” resets the state and subscriptions. The same control has separate level and simple-calibration buttons that set parameter 5 to 2 and 4 respectively. These are source observations, not UI execution results.

`MAVLinkInterface.doCommand` sends the `COMMAND_LONG` first, then has a special case for full accelerometer calibration (`PREFLIGHT_CALIBRATION`, parameter 5 equal to 1): it returns true without waiting for an ACK, even when `requireack` is true. Thus the source control's true-return branch cannot by itself establish vehicle acceptance. The disarmed test below observed the separate vehicle ACK in the packet capture.

The REA index for the release executable contains method bodies for the calibration click, packet callback, level click and simple-calibration click. The click method's static call references include `sendPacket`, `doCommand` and `SubscribeToPacketType`; the callback references `UnSubscribeToPacketType`. Tokens, IL hashes and call records are in `mission-planner-binary-evidence/accel-calibration-method-map.json`. These references anchor the source investigation to that executable but do not prove source-to-binary equivalence or actual UI execution.

In `ardupilot-source/ardupilot-master/libraries/GCS_MAVLink/GCS_Common.cpp`, `handle_command_preflight_calibration` rejects the command while soft-armed. For the full-accelerometer selection, `_handle_command_preflight_calibration` first calibrates gyros, initializes accelerometer calibration and starts the calibration state machine. `AP_AccelCal/AP_AccelCal.cpp` requests the current orientation repeatedly while waiting; `gcs_vehicle_position` only schedules collection when the supplied position matches the current step. These describe the examined source and compile-time feature branches, not every board configuration.

`InitialSetup.cs` adds the calibration page when connected and parameter loading is complete. `BackstageViewPage.Page` creates a control lazily and caches it in `_page`; `BackstageView.ActivatePage` calls `Deactivate` on the old page and `Activate` on the selected page. This source path supports reuse when navigating between pages in the same backstage view, but does not establish every way the application may recreate or dispose the view. REA records for `ActivatePage`, `get_Page`, and `set_Page` are in `mission-planner-binary-evidence/backstage-page-method-map.json`; the static call records include `Deactivate`, `Activate`, and `Activator.CreateInstance`.

## Observed start

`research-tools/AccelCalibrationStartProbe.cs` called the original `MissionPlanner.ArduPilot.dll` against disarmed Copter SITL. The probe used the screen's full-calibration command and deliberately sent no position confirmation. The relay recorded one `COMMAND_LONG` with command 241 and parameters `0,0,0,0,1,0,0`; SITL returned an accepted command ACK. The library returned true, then the probe read 12 position requests for level (position 1) over its observation loop. Independent frame decoding found the same 12 requests and no outbound `ACCELCAL_VEHICLE_POS` command. All captured vehicle heartbeats were disarmed.

Raw captures, binary hashes, simulator log and parsed records are in `sitl-evidence/command-ack-calibration_start/`; the decoder is `research-tools/summarize-accel-calibration-start.py`. Calibration was not completed. No UI button, physical motion, sensor quality, saved calibration values, armed rejection or calibration failure handling was tested.

## First position response

A second disposable run used the original library and the same `sendPacket` construction as the control. After the level prompt (position 1), the probe sent position 2; SITL returned a failed ACK and repeated position 1 three times. The probe then sent position 1; SITL returned an accepted ACK and requested position 2. The probe log records that order, and independently decoded uplink and downlink captures contain the corresponding commands and ACKs. The position-response packets had target-system and target-component fields of **0, 0**: those fields were not assigned in the constructed payload, even though the `sendPacket` call was given vehicle identifiers 1, 1. SITL accepted this test's correctly matching response. Multi-vehicle routing and the full control were not tested.

Evidence: `sitl-evidence/command-ack-calibration_step/summary.json`, `research-tools/AccelCalibrationStepProbe.cs`, and `research-tools/summarize-accel-calibration-step.py`. The test stopped at the second prompt; it did not complete calibration or validate physical sensor readings.

## Six simulated orientations

The source-built Copter binary also has a `calibration` simulator model. Its attitude-control mode uses simulated servo outputs 5–8 to select and set orientation; see `libraries/AP_HAL_SITL/SITL_cmdline.cpp` and `libraries/SITL/SIM_Calibration.cpp`. In a separate disposable run, `AccelCalibrationFullProbe.cs` used the original Mission Planner library to issue the calibration start and simulate all six requested positions. It set the model's servo values, waited 4.5 seconds per pose, then sent the requested position. The simulator acknowledged all six responses and emitted `Calibration successful`. A decoder independently found the start, all six position commands and accepted ACKs, and the success status text. The 22 servo commands were also acknowledged. Captured heartbeats remained disarmed.

Evidence, including the relay and probe source snapshots, is in `sitl-evidence/command-ack-calibration_full/summary.json`; `research-tools/summarize-accel-calibration-full.py` decodes the raw captures. This establishes one complete **simulator-reported** calibration through library calls. The test did not independently measure simulated attitude, use the full Mission Planner UI, or calibrate physical hardware. The servo commands are specific to this SITL model.

The first run's downlink contained offsets, scales and IDs emitted after the sixth position and before the success message. A separate simulator process restarted from a byte-identical **copy** of that run's `eeprom.bin`; a standalone MAVLink client read back 14 accelerometer ID, offset and scale values. All 14 exactly matched the values decoded from the first run's downlink. `sitl-evidence/accel-calibration-reboot/summary.json` records hashes and the values, and `research-tools/summarize-accel-calibration-reboot.py` independently decodes both captures. This is one simulated reboot and does not establish persistence on a physical controller. The copied storage changed during simulator startup and shutdown; the pre-restart copy is preserved separately.

## Armed rejection and early return

Two additional tests force-armed a **disposable simulator**, observed an armed heartbeat and called the same original-library method. In both, the method returned true; the captured vehicle response was `MAV_RESULT_FAILED` and `Disarm to allow calibration`. In the first test the probe incorrectly assumed true meant acceptance and exited with an error; its capture and log are retained in `sitl-evidence/command-ack-calibration_armed/`. In the second, the probe continued reading, observed the failed ACK, sent a disarm command and observed a disarmed heartbeat; see `sitl-evidence/command-ack-calibration_armed_observed/`. `research-tools/summarize-accel-calibration-armed.py` checks both captures.

The source control enters its calibration state on the early true return, and its callback resets that state only for status text containing “calibration successful” or “calibration failed.” The observed rejection text contains neither phrase. Forced arming was limited to the disposable simulator.

An attempt to inspect the connected, modified application screen did not reach the calibration control: Windows Computer Use reported `failed to activate captured window` twice. The application script had connected through the file spool and reported the simulated vehicle armed, then disarmed it and observed `final_armed=False` during cleanup. The local relay and simulator exited; the test application required forced termination. Logs are in `sitl-evidence/ui-calibration-armed/`. No calibration UI behavior was observed in that attempt.

Two later instrumented harness runs instantiated the actual WinForms control and invoked its private click handler directly against a forced-armed disposable SITL. The executable and ArduPilot DLL were hash-identical to the distributed copies; Utilities was the test-patched data-path version. After the failed calibration ACK and disarm notice, the control's `_incalibrate` field remained true, its button remained enabled with text `Click when Done`, and its label showed `Disarm to allow calibration`. In the second run, another handler invocation sent `ACCELCAL_VEHICLE_POS` with position 0 and target fields 0,0; SITL returned another failed ACK. Both harnesses received an accepted simulated-disarm command result. Raw packets, probe source and executables are preserved under `sitl-evidence/command-ack-calibration_control/` and `command-ack-calibration_control_retry/`, and `research-tools/summarize-accel-calibration-control.py` independently decodes them.

These observations establish the control's behavior under direct handler invocation in the instrumented process. The control was not rendered, and normal application navigation, a user's physical clicks, screen lifecycle and recovery were not tested. Hardware behavior is not established.

An additional instrumented lifecycle attempt invoked `Deactivate`, `Activate`, then the click handler again after rejection. Reflection counted two subscriptions owned by the control before deactivation, two afterward, and four after the new start. The active flag changed to false on deactivation and remained false on reactivation, but the button text still said `Click when Done`. The second calibration start was also rejected. The harness then sent simulated disarm; the relay captured its accepted ACK, but the harness did not return from the call before a 55-second timeout and was terminated. The reason for that hang is unestablished; it does not prove a hang in normal app use. A previous 90-second lifecycle attempt also timed out, and its packet capture is retained; its wrapper did not save the probe output.

See `sitl-evidence/command-ack-calibration_lifecycle_observed/summary.json` and `research-tools/summarize-accel-calibration-lifecycle.py`. Counts refer to the directly instantiated control and its test connection; they do not establish how often the normal application reuses or disposes a screen.

In a comparison run, the same direct lifecycle steps again produced two retained subscriptions and then four after another start. The harness moved the disarm call to a worker and pumped WinForms messages on the control thread while waiting; that call returned true and the harness exited normally. Both threading and message pumping changed together, so the comparison does not isolate the exact cause of the earlier timeout. It does not prove that the ordinary application hangs. Evidence is in `sitl-evidence/command-ack-calibration_lifecycle_pumped/summary.json`, decoded by `research-tools/summarize-accel-calibration-pumped.py`.

A further instrumented run used the actual `BackstageView` and `BackstageViewPage` classes to switch from the calibration page to a second page and back. It observed the same control object on return. After the rejected start, switching away and back retained the two subscriptions and `Click when Done` text; a further handler invocation created two more subscriptions and the simulator rejected the second start. This process used the original, hash-matching main executable, ArduPilot and Controls assemblies with the patched Utilities assembly. It used a worker and message pump for disarm and exited normally. Evidence: `sitl-evidence/command-ack-calibration_page_navigation/summary.json` and `research-tools/summarize-accel-calibration-page-navigation.py`. This exercises the page-switching component directly in an unrendered harness; it does not show a user's screen or prove every application navigation path behaves identically.

A related unrendered run then called `BackstageView.Close`. Immediately afterward the calibration control reported `IsDisposed=True`, while reflection still found four entries in the open connection's subscription list whose delegate targets were that control. The connection was closed during cleanup. This demonstrates retained references at that point in this harness; it does not measure memory growth or establish later callback effects in the normal application. The first disposal attempt failed before `Close` because the harness used an ambiguous reflection lookup; the corrected run and decoder are `sitl-evidence/command-ack-calibration_page_close_retry/summary.json` and `research-tools/summarize-accel-calibration-page-close.py`. The failed attempt is retained in `command-ack-calibration_page_close/`.

A further run repeated the disposal sequence, then started another calibration on the now-disarmed simulator while the connection remained open. Subsequent packets reached the retained callbacks: the library logged 22 `InvalidOperationException` instances whose stacks included the disposed control's `UpdateUserMessage` and `PacketReceived`. The harness continued processing and exited successfully. The new simulator calibration was not completed. Captures and log are in `sitl-evidence/command-ack-calibration_disposed_callback/`; `research-tools/summarize-accel-calibration-disposed-callback.py` validates the recorded sequence. This demonstrates logged callback failures in the instrumented process, not a measured application crash or normal-user impact.
