# Firmware workflow source trace

Scope: selected paths in Mission Planner 1.3.83 and the synthetic parser tests below. This is not a validation of firmware authenticity, board compatibility, bootloader behavior or a successful flash. No hardware was connected or flashed.

`GCSViews/InitialSetup.cs` conditionally registers firmware-related pages. `GCSViews/ConfigurationView/ConfigFirmwareManifest.cs:67` calls `APFirmware.GetList` with a configured manifest URL. The page's vehicle-image handler at `:182` asks the user to confirm before starting its port-selection path.

`LookForPort` at `:193` enumerates platform COM ports and optional extra-device providers. It uses a detected board ID or derives candidates from device information, then filters firmware manifest entries by board ID and selected MAV type. Depending on the available options it selects or asks for a firmware choice. It downloads the selected URL to a temporary file and calls `Firmware.UploadFlash` with the selected device and file (`:333`–`:337`). There are additional manual and DFU paths elsewhere in the same view; the description here does not cover all of them.

`Utilities/Firmware.cs:1292` dispatches `UploadFlash` according to the board enum. The source includes a PX4-family path, VRBrain, Parrot, Solo and a fallback Arduino path. The Arduino path parses an Intel HEX file and selects an Arduino communications implementation. The source includes other checks and uploader-specific behavior; board detection alone does not establish that the firmware file is correct for a specific device.

## Synthetic firmware parser tests

`Utilities/Firmware.cs:597` calls `px4uploader.Firmware.ProcessFirmware`. In the 1.3.83 source, that parser deserializes the file, base64-decodes and decompresses its `image`, and allocates using the declared `image_size` (`ExtLibs/px4uploader/Firmware.cs:94`). It performs one decompression read without checking the returned byte count and pads the allocated array to a four-byte boundary (`:107`–`:122`). REA indexed the distributed library's two `ProcessFirmware` overloads as tokens `0x06000002` and `0x06000003` in `rea-extended-index.sqlite`; member identity alone does not prove complete source equivalence.

A local harness called the distributed `px4uploader.dll` with five synthetic APJ-shaped JSON files using board ID 9999 and compressed ASCII data. For a file declaring eight image bytes but containing only four decompressed bytes, the parser returned an eight-byte array containing `ABCD` followed by four zero bytes without throwing. Valid three- and seven-byte synthetic images produced arrays of eight and twelve bytes respectively; the five-byte case produced eight bytes. Independent Python zlib decompression and fixture hashes are recorded in `sitl-evidence/firmware-parser-probe/verification.json`, with the parser transcript in `probe.log`. These cases characterize the parser's returned data, not the subsequent uploader, board checks or the safety of a flash. Do not treat successful parsing as proof that a firmware image is complete or authentic.

Four malformed or boundary fixtures were tested separately (`sitl-evidence/firmware-parser-invalid/`). Invalid base64 raised `System.FormatException`. Invalid zlib bytes produced a `Possible bad file` message but returned a four-byte zero array; a truncated compressed stream returned `41 00 00 00`. With `image_size=0`, the parser returned a null image array. Independent Python base64/zlib checks rejected the first three compressed inputs. These outputs concern this library call on synthetic inputs; whether subsequent firmware-upload code rejects any of them has not been tested.

## In-memory uploader test

The uploader's `upload` method checks board ID and declared internal/external sizes before its erase and program calls (`ExtLibs/px4uploader/Uploader.cs:918`). A standalone harness supplied an `ICommsSerial` fake implemented entirely in memory, manually set the uploader's reported board ID, maximum size and bootloader revision, and supplied synthetic 252-byte-declared images. A mismatched board ID and an undersized mock flash each raised an exception with zero mock writes. With matching fields, the uploader sent erase, program, verify and reboot commands to the fake. The fake stored program bytes in memory and echoed them for the revision-2 verification path.

For the fixture with 248 decompressed bytes and a declared size of 252, the mock captured 248 `A` bytes followed by four zeros; the uploader returned normally. The complete 252-byte control was also accepted. The captured bytes were compared with independent Python zlib output (`sitl-evidence/mock-uploader-probe-2/verification.json`). A separate matching-board mock run used invalid zlib bytes with the same declared size: the parser printed `Possible bad file`, and the fake captured 252 zero bytes before the uploader returned normally (`sitl-evidence/mock-uploader-invalid/`). These results show the tested uploader path did not reject those synthetic images before sending parser-produced bytes to this fake. The fake does not establish real bootloader behavior, board detection, authenticity checks elsewhere, or hardware flashing; no operating-system serial port was opened. The first mock run and its transcript are retained separately in `mock-uploader-probe/`.

Another fake-bootloader run returned a failure response to the erase command. The uploader raised `bootloader reports OPERATION FAILED`, sent no program bytes and did not send a reboot. When the fake instead altered one byte in its revision-2 verification response, the uploader raised `Verification failed` and did not send a reboot. A matching control completed (`sitl-evidence/mock-uploader-faults/probe.log`). The harness's `erased=True` field means that the fake received an erase command; it does not assert that an erase succeeded. These are simulated responses, not observations of physical-device recovery.

For a simulated revision-3 bootloader, the fake calculated a CRC over the 252 programmed bytes plus `0xff` padding to its manually configured 512-byte flash size. A matching CRC completed the mock upload and issued the fake reboot command; flipping one CRC bit caused `Program CRC failed` with no reboot (`sitl-evidence/mock-uploader-crc/probe.log`). This checks the uploader's response to two controlled CRC values from an in-memory fake. It does not test a real device's CRC, flash layout or recovery.

No manifest request, board enumeration, download, real bootloader exchange, hardware flashing, hardware verification or firmware UI action was exercised in this trace. The source paths are starting points for separate tests with mocks or disposable test equipment.
