# Copter mode labels in Mission Planner DataFlash text exports

With Mission Planner 1.3.83's bundled parameter metadata, the desktop application's log-conversion callback supplied names for 25 of the 26 mode numbers in the pinned Copter firmware. Mode 28 (`TURTLE`) appeared as `28`. Mode 26 (`AUTOROTATE`) appeared as `Heli_Autorotate`, and mode 27 (`AUTO_RTL`) appeared as `Auto RTL`. The adjacent `ModeNum` column kept the numeric ID in every record. [Converted output](sitl-evidence/copter-log-mode-labels/with-handler.log) · [Pinned Copter enum](ardupilot-source/ardupilot-master/ArduCopter/mode.h)

A single synthetic DataFlash file contained a LOITER record, a Copter firmware identification message, then one MODE record for each number from 0 through 30. The initial record read `MODE, 1, 5, 5, 0`. When the same mode recurred after the message, the output read `MODE, 8, Loiter, 5, 0`. A second conversion in the same process used the library with no desktop callback and produced numbers in all 32 mode records. [Fixture](sitl-evidence/copter-log-mode-labels/mode-series.bin) · [Numeric control](sitl-evidence/copter-log-mode-labels/without-handler.log)

The probe subscribed the compiled `MainV2` callback (method token `0x06000232`) to the release library's `BinaryLog.onFlightMode` event. The probe seeded one entry in the metadata cache with the original `ArduCopter2/FLTMODE1/Values` string from `ParameterMetaDataBackup.xml`. This fixed the metadata input for both runs. The release source looks up the mode in the vehicle's FLTMODE1 list, and the binary reader prints the decimal number when the callback returns null. A downloaded or user-supplied metadata catalogue can supply different names. The test exercised the conversion handler in a harness. The desktop Log Browser, live mode selection and firmware mode entry were outside its scope. On Windows, run `python -B research-tools/verify-copter-log-mode-labels.py` from the repository root. It compares five release files against the portable ZIP, compiles the probe in a temporary directory and checks that the regenerated fixture and both outputs match the saved bytes. It checks each mode field, timestamp, mode number and reason against the expected sequence and checks that the fixture covers the firmware enum.
